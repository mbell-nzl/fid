## The task

CI runs the Go tests in four shards (#108). `.github/scripts/ci_tests.py` assigns each test name to a shard so that
the shards' total measured test time is equal, using the per-test seconds in `.github/scripts/durations.json`. That
total is the wrong measure. A shard runs its race packages, then its plain packages, and `go test` runs each group's
packages concurrently, so a shard's wall time is set mostly by its slowest package in each group. #113 regenerated
`durations.json` from a four-shard run and changed nothing else: on its own run (45354196371) the four tests jobs
still took 3m35s, 6m35s, 6m51s and 7m28s. Across the shards, `cmd/fid` took 149, 314, 333 and 341 s, and
`internal/journal` 79, 175, 257 and 358 s.

Acceptance criteria (in fid):

1. The splitter plans by each shard's predicted wall time, for example by spreading each heavy package's tests
   evenly across the shards, and `durations.json` is regenerated from a current four-shard run.
2. The PR's own CI shows the four tests jobs finishing within about a minute of each other, and the PR reports each
   shard's predicted and actual time.
3. The exhaustive plan check still passes (every package and target in exactly one shard), and `ci_tests.py`'s unit
   tests cover the new planning rule.

## The design (settled; deviations go to the report)

- **The unit stays a test name.** `-run` selects a name in every package that has it, so a name and all its packages
  go to one shard together, as now.
- **The objective changes.** Predict a shard's wall time as, for each of its two groups (race, then plain), the larger
  of its slowest package's share and the group's total divided by the parallelism `go test` uses on CI's runner, plus
  a fixed setup time; sum the two groups. Assign names, heaviest first, to the shard whose predicted wall time grows
  least. Fit the model's parallelism and setup constants to #113's run (its shard logs, below) and say in the report
  how well the model predicts those four shards.
- **`plan` prints the prediction**: each shard's predicted wall time, its slowest package per group, and the totals,
  then the exhaustive check as today.
- **The data**: regenerate `durations.json` with `ci_tests.py durations` from all four shards' `tests-plain.jsonl`
  and `tests-race.jsonl` of a current main run. Your sandbox has no network, so the orchestrator downloads them
  before the build to `.cache/ci-shards/<run>/shard-<n>/` in the main checkout (the folder above
  `git rev-parse --path-format=absolute --git-common-dir`), together with #113's run as
  `.cache/ci-shards/45354196371/`. Name both runs in the report.
- No workflow change: `.github/workflows/**` stays as it is.
