- An epic has up to 10 validations. That is a soft cap: more means the epic
  should be split.
- Each validation names a verifier: `check:`, `review:` or `human`. A human
  one needs a fixture recipe.
- Approving an epic is a person's decision. It binds to the validation list
  only, since builders update briefs and specs in their PRs.
- `next` skips tasks in an unapproved epic, with a typed reason.
- Agent-created work that blocks a task in an approved epic joins that epic
  (`blocks`, `discovered_from`), keeps its own lane, and is served without a
  person's acceptance.
- Epics close by a person with `fid done <epic>`, which is refused while any
  of the epic's tasks is open. 3.1 adds the epic's validations to that check.
- NEEDS YOU lists epic plans awaiting approval. `fid show` adds an epic's
  Plan and VALIDATIONS rows after `Spec`.

Mark decided the rest on 2026-11-28:

1. **Approval gates the epic and signs off its plan.**
   - `next` serves an epic's unstarted tasks only while its approval is
     current.
   - Approving shows the plan (tasks, lanes and validations) and accepts
     the agent-created tasks in it.
   - Editing the validation list makes the approval stale. Started work
     carries on; unstarted tasks wait until he approves again.
   - A task added later is ready at once if a person created it. An agent's
     task still needs acceptance, unless it blocks a task in the epic.
2. **Validations belong to epics only.** Tasks keep acceptance criteria.
   The commands sit under `fid epic`.
3. **fid proves the check claims; a person records the rest.**
   - `check:<name>` names a `.fid.toml` check. fid runs it on the default
     branch once the epic's tasks have merged, and records the result
     against that commit. A check that no lane lists runs only for
     validations.
   - A person records `review:<profile>` and `human` passes. fid shows the
     evidence beside each: the epic's rounds with that profile, or the
     recipe.
   - `fid done <epic>` refuses, listing each validation without a current
     pass.

## Approved design

The command names follow the CLI spec's rules. If a rule there needs a
different spelling, follow the rule and say so in the report.

- **Validations.**
  - Add: `fid epic validation add <epic> --claim <text> --verifier <verifier>
    [--recipe <path>] --actor <actor> --idempotency-key <key>`, where the
    verifier is `check:<name>`, `review:<profile>` or `human`.
  - IDs: fid assigns the epic's next ID (V1, V2 and so on) and never reuses
    one.
  - Update and remove follow the same rules. Agents and people may add,
    edit and remove validations.
  - A `check:` name must be a check in the effective policy from the
    default branch, as V7 requires. A `review:` name must be a profile fid
    knows.
  - `human` requires `--recipe`: a project-relative path, normalized like
    `spec_md_path`. The file need not exist yet, because a builder may
    write it in a later PR.
  - An eleventh validation adds a warning, never a refusal.
- **Epic approval.** `fid epic approve <epic> --actor human:<name> --reason
  <why> [--idempotency-key <key>]`.
  - It is person-only and interactive, like `fid approve`: a preview, then
    the epic's ID typed to confirm.
  - The preview lists the epic's tasks with their lanes and states, its
    validations with their verifiers, and the agent-created tasks that
    approving will accept.
  - Take the write lock only after the confirmation. Then check that the
    plan still matches the preview, and refuse with a retry message if it
    changed. `fid approve` currently holds the lock while it waits;
    FID-62b7bb fixes that, so don't copy it.
  - Recording appends one person decision. It binds to a digest of the
    validation list (IDs, claims, verifiers and recipe paths). In the same
    write it accepts each unaccepted agent-created task or subtask then in
    the epic.
  - An empty validation list may be approved.
  - Any later add, edit or remove makes the approval stale. Approving
    again makes it current. Reuse 2.3's current/stale display.
- **`next`.**
  - Skip an epic's unstarted tasks while it has no current approval, with a
    typed reason, as unaccepted tasks are skipped now: `none` with
    `waiting` null.
  - A worktree's kept build hold or review reservation still occupies it.
  - Started work in that epic is still served: resume, rework, review and
    judge items.
  - Tasks with no epic are unaffected.
  - Reasons are informational, so the contract stays `fid-cli.v2`.
- **Discovered blockers.** An agent-created task or subtask is served
  without acceptance when all of these hold:
  - it is in an epic with a current approval;
  - it blocks one of that epic's open tasks.

  It keeps its own lane and its `discovered_from` link. Other
  agent-created work still needs acceptance.
- **Verifying check validations.** `fid epic validation verify <epic>
  --actor <actor> --idempotency-key <key>`.
  - It runs each `check:` validation's check: the `.fid.toml` definition,
    timeout and artifacts, executed as `fid check` executes them.
  - It runs on a clean checkout of a default-branch commit that contains
    the merge commit of every completed task in the epic, and records pass
    or fail against that commit.
  - Any actor may run it.
  - It refuses while the epic has open tasks.
  - You choose where it runs, for example a temporary detached worktree
    that fid creates and removes. It must never touch the caller's working
    tree.
- **A person's pass.** `fid epic validation pass <epic> <id> --actor
  human:<name> --reason <why> [--idempotency-key <key>]`.
  - It is person-only, and only for `review:` and `human` validations: fid
    proves `check:` ones itself.
  - It is recorded against the locally known default-branch commit, which
    must contain every completed task's merge.
  - For a human validation, the recipe must exist in that commit.
- **When a pass is current.** A pass is current while both hold:
  - its commit contains the merge of every completed task in the epic;
  - the validation hasn't changed since the pass.

  A later merge into the epic, or an edit, makes it stale.
- **`fid done <epic>`.** Keep the existing refusal for open tasks. Add
  refusals when:
  - the epic has no current approval;
  - any validation has no current pass (none recorded, stale, or failed).

  The refusal lists each validation with its verifier and what's missing.
- **`fid show <epic>`.** After `Spec`, in 1.3b's order:
  - an Approval row: current, stale or missing, with who approved and when;
  - Plan;
  - VALIDATIONS: each validation's ID, claim, verifier, recipe, and pass
    state with its commit.
- **`fid status` NEEDS YOU.**
  - An epic with unstarted tasks and no current approval gets an item to
    approve the plan, with the command.
  - An epic whose tasks are all done gets an item saying what each
    validation still needs (verify, or a person's pass), before the
    existing close item.
  - JSON adds only optional fields.
- **The loop.**
  - At its `none` and done batch, for each epic in scope whose tasks are
    all done and which has a `check:` validation without a current pass,
    run `fid epic validation verify` once, as the builder actor.
  - It reports the outcome. A failed check is reported and never retried
    in a loop.
  - Declare the verify reply in the contract. It is additive, so the
    version stays `fid-cli.v2`.
  - The loop never approves an epic or records a person's pass.
- **Records.** Each validation change, approval, verify result and pass is
  a journal event.
  - Replay, rebuild, export, import and restore keep all of them; extend
    V8 to cover them.
  - The migration has a down path.
- **Rollout.** When this merges, every open epic starts unapproved, so the
  loop serves no unstarted task until Mark approves an epic. Say so in the
  report.

   - **Validations:** add, update and remove; IDs are never reused; the
     verifier forms; `check:` names come from the default branch's policy;
     `human` needs a recipe; the eleventh validation's warning.
   - **Approval:**
     - person-only and interactive; the preview; the retry key; an empty

     - each kind of edit makes it stale, and approving again makes it
       current;

       changed after the preview is refused.
   - **`next`:**
     - an unapproved or stale epic's unstarted tasks are skipped with the
       reason;
     - started work in that epic is still served;
     - tasks with no epic are unaffected;
     - the discovered-blocker exception and its limits: work that blocks
       nothing, a blocker in another epic, an epic that isn't approved.
   - **Verify:**
     - it runs on a clean default-branch commit that contains the epic's
       merges, and records both pass and fail;
     - it refuses with open tasks or the wrong commit;
     - it never touches the caller's tree.
   - **A person's pass:**
     - it is person-only, refused for `check:` validations, and recorded
       against the default-branch commit;
     - a later merge into the epic makes it stale, and so does an edit.
   - **`fid done <epic>`:** each refusal (no approval, stale approval, a
     missing, stale or failed pass) and success.
   - **Display and records:** `show` and `status` in text and JSON; replay,
     rebuild, export/import and restore.
   - **The loop:**
