fid and Kit Reset

Revised after independent review and research 29 October 2026, during Phase 24 Human QA Sources: the fid, kit, whet, kauri and atlas repositories, the Codex landscape report, and our conversation

After five months, fid and the kit both hold real engineering, but neither is in daily use. They have been blocking each other, and the workflow built to make them has turned into agent waterfall. This proposal narrows fid to a ledger that proves agent work, with a human interface as good as whet's. It reduces the kit to a small skills plugin. It starts with a thin facade over fid's existing kernel and settles five foundations before any code changes. Rigour moves out of prose and into tests, receipts and records that fid enforces.

Agents write the code.
The kit: technique, as skills and one reviewer agent.
Tools prove it.
fid: state and evidence, held deterministically.
Humans decide.
fid's human CLI: drop in, see the situation, approve or redirect.

What changed in this revision.

  • An independent Opus 5.5 review ran experiments against the repositories (section 16). As a result:
    • fid now gets a facade over its existing kernel instead of a concept collapse.
    • Five foundations are settled first: where the ledger lives, worktrees, the trust anchor for checks, approval integrity, and what "done" means.
    • Lanes are computed by fid and the plan is approved by you.
    • The loop reads fid state instead of exit codes.
    • The measurement plan is stronger, and several facts are corrected.
  • The Codex research report (section 15) confirmed the core direction and tightened the hook, receipt and reviewer claims.

1What you set out to do

The goal under both projects, in your words and from the original charter.

"I was excited about the idea of trying to craft my own tools and figure out for myself the best ways to build agent-driven engineering workflows, i.e. agents write all code and review most of it, but the engineering quality is high."You, in this conversation

Three goals ran through the work:

  1. Learn by building. Find out how far agent-driven development can go when the engineering bar stays high, by making the tools yourself instead of adopting someone else's method. whet was the first round of this; its README calls it "a deliberate learning exercise".
  2. fid: durable state for agents. The May spec described a local-first, agent-first issue tracker. Hash-based IDs let parallel agents create issues without coordinating. An append-only journal makes state survive sessions and chat compaction. Machine-readable output keeps agents cheap to run. The charter later added the core principle: evidence is observed, not reported.
  3. The kit: a reusable method. A versioned engineering workflow you could install in any repository and run with Codex or Claude Code. It keeps project truth separate from the method, and asks for human judgment only where it matters.

Those goals still hold up. The research report finds the same gaps across the industry: durable state outside the conversation, trusted evidence that work was done, and human attention as the scarce resource.

4fid on one page

What fid becomes.

fidLocal-first work ledger with receipts · Go · SQLite + append-only journal

A work ledger with receipts for agent-written code. Git records what changed. fid records whether it was proven, and refuses "done" until it is.

What it does

  • Tracks epics, tasks and subtasks with dependencies, acceptance criteria and a lane.
  • Records proof:
    • a registered check ran on this tree and passed;
    • a reviewer in a separate session reviewed it;
    • you approved this exact change.
  • Computes the lane floor from what changed, and refuses "done" until the lane's evidence is there.
  • Holds an epic's validations and closes the epic only when each one is met or waived by you.
  • Answers "what's next?" deterministically and claims the work atomically.
  • Talks to people through a whet-quality CLI and to agents through --json. The human view is rendered from the same JSON.

What it stops being

  • A backend for the kit, or a party to capability negotiation.
  • A store for specs, decisions or status prose.
  • A role system, or a surface where callers manage Envelopes, Runs, revisions and keys by hand.

How it gets there

  • Facade first. Golden-path commands compose existing kernel leaves. 57k of the 87k test lines touch activation, Envelope, Claim or Run, so collapse internals later, and only where the facade leaks.
  • Foundations first. Five decisions come before code (section 7).

What stays from the kernel

  • Journal as the record; SQLite rebuilt from it.
  • Evidence is observed, not reported.
  • Fail closed when authority, evidence or repository state is missing.

5The kit on one page

What the kit becomes.

Agentic Engineering KitYour engineering method as a skills plugin · Claude Code and Codex

Your engineering method, packaged as a handful of skills, one reviewer agent and a short loop. It shows agents how to plan, build and review to your standard. fid enforces the policy; the kit explains it.

Contents

  • plan: write the epic brief, slice it into tasks with ACs, and propose 5–15 validations for you to approve.
  • tdd: red/green on observable behaviour. Skip it for wiring and configuration, as Pocock's guide advises.
  • reviewer agent: read-only tools plus fid review, parameterised by profile (code, test adequacy, security). It runs in a separate session, and on another model for Assured work.
  • verify-app: drive the real CLI or app, not only unit tests. Adapted from pstack's create-verification-skill.
  • handoff: turn fid brief into a short human brief.
  • The loop: a short script that reads fid state and stops when you're needed (section 14).

Principles

  • Borrow technique, own policy. Take generic skills from reputable libraries. Write your own only where your method differs.
  • Boundaries, not personas. A subagent earns its place by a different context, permissions or model, not by a job title.
  • Technique in skills, state in fid, sequence in code.
  • One-way dependency. The kit calls fid --json; fid knows nothing about the kit. The loop needs fid; the skills don't.
  • Per-project policy (lanes, checks, protected paths, owned paths) lives in one project file. The kit pins a fid version range.

Leaves

  • The V2 package manager and activation rollback. Tag and archive them; the sync script remains the installer.
  • The Phase Runner and TL-Lite roles, and the workflow verifier scripts.
  • Per-phase status, triage and escalation files.

Lessons the five months taught

These belong at the top of the kit's README.

  1. Orchestration bloats, in prose and in code; small skills don't. Put technique in skills, state in a tool and sequencing in a short script with a line budget.
  2. Agents' claims need receipts. "Tests pass" means nothing without proof bound to the tree that was tested.
  3. Receipts can't catch weak tests. Most review findings were about test adequacy, so review needs a test-adequacy profile.
  4. A separate-session reviewer catches real defects. Keep the reviewer and drop the paperwork around it.
  5. Status prose is a poor shared memory. Durable state belongs in a queryable tool.
  6. Humans should judge experiences, not rows. Human QA found real defects twice. HUMAN-01 said more than the other 130 rows.
  7. Contracts between unadopted products are pure cost. Build one thing someone uses, then integrate.
  8. The lighter workflow already works. In atlas: owned paths, one integrator, a verification reviewer, and promotion only by you.

7Foundations to settle first

The independent review found that the first draft was silent on these. Each one changes the design, so each is decided before code. Recommendations are marked.

F1Where the ledger lives

ADR-0001 says journal merges are "textual JSONL line-merges, handled by git merge". The reviewer tested this. Two branches that each create and update issues produce a merge conflict. Keeping both sides yields duplicate event IDs and sequence numbers, and then fid rebuild and fid issue list both fail with exit 6. The cause is event IDs drawn from a per-day counter, and replay that requires contiguous sequences. A committed journal also changes the tree, which makes every receipt stale. fid's own repo ignores /.fid/, so this was never exercised.

  • Option A: keep the ledger out of git, at $(git rev-parse --git-common-dir)/fid/, with fid export for backup. Every worktree shares one ledger automatically.
  • Option B: make events merge-safe (content-hash IDs, per-writer files, replay that tolerates any order) and exclude .fid/ from the freshness tree.
Recommended: A. It also solves F2. Add a two-branch scenario to the golden-path test. Revisit B only if you need the ledger on more than one machine.
F2Worktrees and parallel agents

Project discovery stops at the git boundary, so each linked worktree sees its own ledger or none. Claims in one worktree are invisible to another. WorktreeID is a hash of the root path, so a receipt never moves between worktrees. Parallel claim semantics (work.claims.v1, roadmap Phase 25) are unbuilt. atlas already runs 12 worktrees.

Recommended: use a shared ledger (F1 option A) with claims keyed to issue and worktree, and an atomic fid next --claim. Builders can then run in parallel on different issues. Conflicts between shared files are handled by atlas-style owned paths and an integrator, then caught by CI at merge. ADR-0006's proofs of disjoint scope wait for real need.
F3The trust anchor for checks and authority

Today, Kit Activation supplies gate definitions (argv, cwd, environment, timeout) and the actor authority profile. The V2 session's Gate B3 says fid never treats a mutable authoring file as runtime authority. Simply "configuring checks in .fid/" would break that. Separately, make test runs code the agent can edit in the same diff.

Recommended:
  • fid init creates a local self-activation, and fid check add registers an immutable check that needs your approval.
  • fid records digests of the files that define a check (Makefile, test configuration, CI workflow).
  • A diff that touches those files, or deletes or skips tests, requires a test-adequacy review and raises the lane.
  • The environment allowlist stays.
F4Threat model and approval integrity

The first draft called the terminal prompt the source of approval integrity. That's wrong: an agent can get a pseudo-terminal through script or expect. Actor IDs are labels; in HUMAN-01j you had to act as agent:builder. Human-outcome Obligations are also set to no freshness, so an approval survives any later code change.

Recommended:
  • State the model plainly: honest but fallible agents on a single-user machine, as the charter's single-user trust root already assumes.
  • Under that model, the prompt and the PreToolUse hook are friction against mistakes.
  • Bind approvals to the tree, receipt IDs and review IDs, and make them go stale on change.
  • Show the diffstat, checks and review verdict before [y/N].
  • For Assured work, offer a stronger path: an approval on the PR under your GitHub account, or an SSH signature.
F5What "done" means, and when compatibility starts

Local receipts are bound to a worktree and can't follow work to main. CI already runs four test shards on every PR. Under charter sections 7 and 9, the first dogfood ends the freedom to break compatibility.

Recommended:
  • Routine tasks and the inner loop use local receipts.
  • Standard and Assured tasks are done when merged with CI green; fid records the CI check run through gh api as the trusted receipt.
  • Squash the migrations and declare the baseline before dogfooding.
  • Dogfood with a pinned release binary.

8The human interface

fid is agent-first, but it has to be fully usable by a person who drops in. whet shows the standard: ✓ Person added confirmations, a boxed status dashboard grouped by urgency, names instead of IDs, and one assembled prep view. It sits on a small internal/display package (about 330 lines plus tests) on the same stack, which fid can largely copy.

Principles

  1. Human text is the default in a terminal, rendered from the same result as --json. Golden tests cover both. Any change to the fid-cli.v1 error envelope is versioned.
  2. Lead with state and the next action. Explanations go in --help.
  3. Confirm every write with a ✓ line and the next step.
  4. Refusals follow What, Why and Fix, with the real values filled in.
  5. Use short refs and the current task from the branch or claim.
  6. Prompt or open $EDITOR for input when a person is at the terminal. Agents keep JSON input.
  7. Hide the machinery (claims, runs, keys, revisions) unless --verbose asks for it.
  8. Use aligned key/value lines, symbols and colour roles, with a no-colour fallback.

9Agent coordination

Nothing that keeps agents safe is removed. It is hidden from people and made automatic for agents. Two of the first draft's defaults were unsafe and are corrected here.

MechanismWhat it gives agentsAfter the reset
Claim (lease)Only one builder owns a task; a crashed agent's lease expiresfid next --claim claims atomically across worktrees. The owner's writes renew the lease. Tasks waiting on you are parked, releasing the claim, so day-long reviews don't expire anything.
RunA session record with checkpoints; recovery through a linked successor Run (ADR-0007)Created by start. On interrupt the loop calls fid run abandon. fid show offers to resume from the last checkpoint.
Tree bindingReceipts and reviews go stale when the code changesNo change. This is what makes "checks ✓ · current" trustworthy.
StopsCircuit breakers: review-rework-exhausted, budget-exhaustedShown as blockers. fid next stops serving the task until you act.
AuthorityA builder can't approve; the reviewer differs from the builderA default policy from local self-activation (F3). Reviews record a session_ref so separate sessions can be shown.

Defaults, corrected

  • Idempotency key: derived from the canonical request digest plus FID_SESSION, never random per call. Retries after a timeout are then deduplicated automatically.
  • Expected revision: claimed writes are exclusive, and append-only records (reviews, findings, approvals, notes) can't lose updates. Edits to mutable fields without a claim keep the check. Agents pass the revision they read; the human CLI fills it in from a fresh read and says "changed since you looked" on conflict.
  • Actor: set per role by the loop or harness through FID_ACTOR. A non-interactive caller with no actor is refused. It never defaults to human.

How fid next chooses

Today fid ready returns any unstarted task. The reviewer showed it still returns a task blocked by a dependency link. The new order:

  1. Rework first: your claimed or parked tasks with open findings.
  2. Then unstarted tasks whose dependencies are done, in epic sequence and priority order.
  3. Skip tasks that are claimed, blocked, waiting for you, or in an epic whose plan isn't approved.
  4. Every skip has a typed reason code, so fid next --explain can say why nothing is ready.

Stays as prose

  • Epic briefs: one per epic, short, approved by you.
  • Task specs, only where a description and ACs aren't enough.
  • Specs, updated in the same PR as the code.
  • ADRs for decisions that outlive an epic.

  • Completion reports (17% of the archive), which become receipts, reviews and fid show.
  • Run ledgers, progress, triage and escalation files.
  • QA plans and validation contracts, which become validations and tests.
  • Per-phase decision logs: small decisions become notes and waivers.
  • review-M.md, final-review.md and human-checklist.md, which become reviews, findings and fid brief.

The research agrees with keeping documents that settle intent or decisions. Anthropic's AI-native SDLC playbook keeps an intent → spec → plan chain. What it doesn't support is duplicated status and copied validation tables.

11Reviews and findings

fid already has the model. review record takes a profile, coverage, findings with severity (blocker, major, minor, nit) and resolves_finding_ids. finding address records the builder's response. It needs a usable surface and a few rules.

$ fid review FID-71a0c2 --profile code --verdict changes-required \
    --finding "major internal/cli/stop.go:88  Next: line missing for resolved Stops" \
    --finding "minor help text says 'Envelope' where the user sees 'task'"
✓ Review recorded: changes required (1 major, 1 minor) · session rev-7f2c · tree 9b1f…

$ fid finding address F-12 --reason "fixed in 4c1e2a; added render test"
✓ F-12 addressed · awaiting re-review

Rules

  • Open blocker or major findings refuse fid done. A re-review on the new tree closes them.
  • If tests, test data or check-defining files changed, a test-adequacy review is required in every lane, because weak tests were the most common defect.
  • Assured work needs two reviews, one from a different model, for example a reviewer run through codex exec.
  • After three rework cycles fid raises review-rework-exhausted, and the task comes to you.
  • fid finding promote F-13 turns an out-of-scope finding into a new task.
  • A reviewer uses Addy Osmani's criterion: approve when overall code health improves, not when the code is perfect. This avoids taste-driven review loops.

One of the best ideas in the workflow, and the one that grew most out of proportion. The fix is to keep the contract and move its detail into tests.

A validation is a new epic-level record. Today, Obligations belong to Envelope revisions, an Envelope accepts only one gate-evidence Obligation, and acceptance criteria have no verifier. The reset therefore adds a small new schema rather than reusing Obligations as they stand:

  • a validation has an epic, a statement, and a verifier (check:<name>, review:<profile> or human);
  • it is met only by matching evidence on the current tree;
  • acceptance criteria can optionally name a verifier too.

13Risk lanes

14The loop

It replaces the Phase Runner. It decides from fid's state, never from agent exit codes. fid supplies the rework order, caps and stops, so the script stays short.

#!/usr/bin/env bash
# illustrative; check CLI flags against current Claude Code and Codex docs
# fid next serves rework first and skips parked, blocked and unapproved work
set -euo pipefail
trap 'fid run abandon --current --reason interrupted' INT TERM

while task=$(fid next --claim --json | jq -r '.task.id // empty'); [ -n "$task" ]; do
  FID_ACTOR=agent:builder claude -p --output-format json --max-turns 60 \
    "Use the tdd and verify-app skills on fid task $task. Address open findings. Finish with fid check." \
    | fid usage record --task "$task"

  profile=$(fid show "$task" --json | jq -r '.review.required_profile')   # code, test-adequacy, security…
  FID_ACTOR=agent:reviewer codex exec --json \
    "Use the reviewer skill with profile $profile on fid task $task; record it with fid review." \
    | fid usage record --task "$task"

  case $(fid show "$task" --json | jq -r '.next.kind') in
    ready-to-complete) fid done "$task" ;;
    rework|needs-human|blocked) ;;                       # fid decides what comes back, and when
    *) echo "unexpected state for $task" >&2; break ;;
  esac
done
  • Caps live in fid: per-task turn and token budgets (budget-exhausted) and three rework cycles (review-rework-exhausted).
  • Usage is captured from claude -p --output-format json and codex exec --json, so tokens per task are measured, not guessed.
  • Parallel: run one loop per worktree. fid next --claim is atomic over the shared ledger.
  • Tests for the loop: port the kit's V2-2 harness scenarios (rework, budgets, interruption, parallel isolation). Give the loop a line budget, so it doesn't grow into a new 4,700-line verifier.
  • Hooks are not the enforcement. The research found that blocking depends on exit codes, timeouts and per-event semantics, and differs between hosts. A small conformance test per host checks the friction hooks still work.

Diagnosis

  • fid was validated as software, never as a tool.
  • The ten-task trial was deferred, and five heavy phases followed.
  • The kit and fid were blocked on each other's contracts.
  • HUMAN-01 failures point to too many concepts.
  • Most review findings were weak tests.

The trial

This follows the viability review's design, with the kit quality plan's thresholds.

  • Ten tasks of comparable size, pre-registered:
    • 4 run with fid and the kit;
    • 3 run with a competitor (Beads or Backlog.md plus a verification skill);
    • 3 run with your Markdown workflow (baseline).
  • For each task, record:
    • active human minutes (manual log);
    • tokens (captured);
    • rework cycles;
    • workflow words written;
    • defects found later;
    • your answer to "would you choose this path again?"
  • Seeded defects: run run-drills.sh against each path.

Kill criteria, set in advance

  • Workflow words fall by at least 70% against the baseline.
  • fid catches at least two false, stale or inadequate claims that the other paths miss.
  • Human attention or tokens fall by at least 25%, and seeded-defect detection is no worse than the baseline. Any quality regression blocks adoption.
  • A fresh agent resumes an interrupted task from fid alone, and you take control of a stuck task in under five minutes with no outside help.
  • You would choose fid voluntarily for the next task.

If the criteria fail, keep the receipts core as a small library or hook pack and stop building fid as a product. Either way you'll know.

Deliberately not doing

  • Rewriting from scratch, or collapsing kernel concepts before the facade shows where it leaks.
  • Adding a TUI, dashboard, MCP server or web UI before daily use asks for one.
  • Per-phase decision logs. ADRs are only for decisions that outlive an epic.
  • Parallel-scope proofs, multi-machine sync or signed attestations until a real need appears.

19How to run the reset

Neither the V1 flow nor an unstructured "just do it". The reset is run with the new method, by hand, before the tool for it exists. Each step moves into fid as soon as that piece works.

Why not the V1 flow

By the workflow's own triggers, the reset is a public-interface and persistence change, so it would be classified Heavy. It would bring back the waterfall: a validation contract, QA windows, completion reports and another 200k words. The V1 flow has one remaining use, as the Markdown baseline arm of the trial, on small kauri tasks.

Why not "just do it"

Most reset tasks are specified well enough for a frontier model to finish in one session. But the foundations are decisions only you can make, and the trust-boundary code is where an unreviewed agent change hurts most. Working without structure would also drop the two things that worked: tests and an independent reviewer.
