What DEC-136 and DEC-138 meant

DEC-136 refresher

Fix the report protocol, preserve strict tokens

Task 4 was told by DEC-135 to make exactly one commit. That was impossible under the canonical protocol: the task commit must exist before its hash can be inserted into the report, then a second docs commit finalizes that report.

The same report also shortened real Go output to fragments such as 4.625s. Those fragments lost the required ok or FAIL marker.

DEC-136 withdrew the one-commit instruction, required fresh exact gate evidence, kept the token checks strict, and established that task specs must not restate or override shared process.

Review: sound. Retain it in V1 and carry the principle into V2.

DEC-138 refresher

Allow narrow bookkeeping repair in-session

After Task 5 added a legitimate integration journey, a hardcoded journey inventory became stale. DEC-138 allowed the same Developer to repair and rerun a gate only when the mismatch was a self-describing repository inventory issue.

Its safeguards required an exact named discrepancy, no threshold or assertion weakening, a byte-identical rerun, and both failure and success tokens. Its shorthand was: fix the bookkeeping, never the verdict.

Review: good safeguards, wrong abstraction. V1 already says to fix an in-scope gate failure and rerun it. The bookkeeping-only category creates ambiguity and fails to cover one of its own examples.

The key correction: the binding V1 workflow does not generally forbid same-session repair. 09_AI_WORKFLOW.md says, "If any gate fails, fix the issue and rerun the exact failed command." AGENTS.md requires a stop only when the failure cannot be fixed inside assigned scope. DEC-138 should not reinforce the opposite interpretation.

The new Task 8 stop

  • Task 8
    Implementation completed. Commit 4df4d66 migrated the issue read contract. Commit ce282c2 finalized its completion report.
  • Report
    Six gates were recorded PASS. The report contains plausible final output tokens, including race/coverage output and a 4.971s dedicated integration result.
  • 19:55
    The Phase Runner stopped at ESC-20-008. None of the six rows contains a nested exit_code or explicit termination result.
Assessment: the Phase Runner followed its current prompt correctly, and the Task 8 report cannot prove termination under that rule. However, the rule is not implementable through the current completion-report template. This is a workflow interface defect, not evidence that Task 8 product code or tests failed.

This defect is directly related to the earlier ESC-20-003 recovery change in commit d0bffbc. That change correctly taught Codex agents to retain nested sessions and wait for a real terminal result. It also told the Phase Runner to reject reports without that result, but it did not add a termination field to the report template or make report-lint.sh enforce one.

A final Go package line is a useful output token, but it is not by itself proof that the entire process exited. The correct fix is to carry the observed terminal status through the evidence interface, not to weaken the Phase Runner back to accepting output alone.

Review findings

HighEvidence schema mismatch

The Developer prompt demands observed termination, the report template has no terminal-status field, and the Phase Runner requires that missing field. Task 8 is the deterministic result.

HighFalse DEC-138 premise

The analysis says Developers may never repair a failed required gate in-session. Binding V1 text says the opposite for repairs inside accepted scope.

HighClassifier weakened

DEC-137 changed an exact dedicated-journey manifest into required-presence only. Because the repository-wide classifier skips the dedicated directory, a future in-process tagged test added there can now evade both checks.

MedDEC-138 is inconsistent

An unused production helper is not a stale inventory assertion, and deleting it requires a judgment about intended behavior. The rule's Task 4 example does not meet its own stated conditions.

MedHistorical claim overstated

The claim that all roughly 26 escalations were verification-only is false. Phase 18 recorded and fixed a real workflow.Load deadlock. Counts also mix ESC records with triages.

MedWorkflow lint is red

The current tree fails only the current-escalation line budget: 142 > 107. The file is accumulating archive prose despite being defined as open items only.

Why the Task 5 classifier change should be revised

The dedicated package originally used an exact list to make every real-process journey intentional. DEC-137 retained only the four historic names and allowed arbitrary additions. Meanwhile, the repository-wide tagged-test walk deliberately skips the dedicated package.

Restore an exact explicit manifest that includes the current fifth journey. An authorized task that adds a real-process journey updates that manifest in the same session. This keeps additions deliberate without requiring a full Tech Lead escalation.

Recommended action plan

Immediate V1 recovery

  1. Fix the evidence handoff before restarting. Add a compact terminal-status field to every required command record, for example termination: exit_code=0, while retaining the separate verbatim output token.
  2. Update all owners of that contract together. Change the completion-report template, Developer prompt, Phase Runner prompt, binding workflow spec, report-lint checks and self-tests, then sync generated prompts.
  3. Recover Task 8 honestly. Re-run the exact six commands in one recording session, preserve each terminal result and token, amend the completion report in a new docs commit, and resolve ESC-20-008.
  4. Supersede DEC-138. State the general rule: a Developer may make a causal repair in the same session when it is inside accepted task scope and changes no protected decision or gate criterion.
  5. Restore the exact journey manifest. Include the current fifth journey and permit authorized additions to update it without escalation.
  6. Archive current escalation history. Return tl_escalations_current.md to open-items-only scope so workflow-lint.sh is green.

The replacement same-session rule

A failed invocation remains failed evidence. The Developer may repair its cause and rerun the exact command when the repair is within accepted task scope, makes no product, architecture, schema, dependency or public-interface decision, and does not weaken the command, assertion, threshold or scope. Record the first failure, root cause, repair, and later terminal result. Stop only when the repair is out of scope, ambiguous, decision-requiring, unrepairable, or beyond the retry budget.

V2 adoption

Do not port DEC-138's bookkeeping category. V2 already treats gate-failed as retryable after scoped repair. Complete that model with immutable attempt records, machine-readable termination receipts, evidence invalidation after tree changes, and explicit retry budgets. A simple gate failure should not require a new run unless the executor or session was actually lost.
