01 / Analytical conclusion

The evidence suggests the V2 plan supplies the product focus fid was missing.

Analyst interpretation Recommendations below This section synthesizes the evidence; it is not an accepted product decision.

The earlier viability review judged fid mainly as a standalone local agentic issue tracker. On that framing, its differentiation and real-use evidence were weak. The V2 kit changes the framing materially: it already has a tested workflow domain and deterministic harness, but deliberately lacks a production source of durable workflow truth and trustworthy execution evidence.

fid has the correct low-level assets for that job: an append-only journal, derived SQLite projection, deterministic rebuild, locking, preconditioned effects, claims, workflows, telemetry, maintenance, and machine-readable output. The roadmap's planned gate receipts, evidence freshness, lean completion, work envelopes, Human brief, and trajectory economics are also pointed in the same direction as V2.

fid does not stop being an issue tracker. Its issues, relationships, acceptance criteria, workflows, ready queue, and claims remain the durable work inventory agents use. V2 adds an execution contract around selected work and a trustworthy account of what happened; it does not replace that inventory with a different kind of task list.

Continue

Continue fid as the local issue tracker, operational work store, trust service, and recovery substrate for V2.

Reslice

Pull the backend port, evidence, idempotency, attention, and portable-export needs ahead of the old feature order.

Do not continue as written

Do not implement the entire role-specific composite, QA-plan, template, and report roadmap before the first production integration.

Analytical correction to the earlier report

The V2 development phase Markdown was produced by the V1 workflow and cannot be used to judge V2's efficiency. It is evidence of why V1 needs replacing. V2's economic outcome remains unmeasured until it runs real work itself.

The first version of this report also conflated two axes: whether a feature is core to fid, and whether it already satisfies the V2 backend port. The revised matrix marks issue creation, reading, updating, transitions, epics, acceptance criteria, workflows, labels, and readiness as Core. Most still need additional envelope bindings or machine-contract semantics before V2 can use them through the port; that is an integration gap, not evidence that they are vestigial.

03 / V1 and V2 workflows

V2 changes how work is executed and evidenced. It does not abolish issues.

Current V1/V2 design Integrated fid interpretation Roles, risk lanes, and V2 responsibilities are sourced; the proposed Issue-to-Envelope relationship is not yet jointly specified.

The word workflow is doing two jobs in these products. An issue workflow is the lifecycle of durable work: captured, ready, active, blocked, reviewed, done. An agentic engineering workflow decides who may act, what context they receive, which checks must run, and what evidence permits completion. fid owns the former and persists the operational facts of the latter; the kit defines the latter's policy.

V1: document-mediated orchestration

V1 is an assurance-first process for an uncertain model era. Roles coordinate through a phase artifact tree, and Markdown carries both durable reasoning and short-lived workflow mechanics.

  1. 1. PlanTech Lead writes a phase brief, decisions, task specs, and validation contract.
  2. 2. DispatchPhase Runner selects tasks and invokes Developer, QA Reviewer, QA Lead, or TL-Lite roles.
  3. 3. ImplementDeveloper works one task, claims scope, runs commands, and writes a completion report.
  4. 4. ReviewReviewer and QA roles write more plans, window reviews, evidence tables, and final review artifacts.
  5. 5. CloseProgress ledgers, carry-forward notes, phase decisions, and a Human checklist reconcile the result.

V2: state-mediated execution

V2 keeps strong engineering controls but compiles routine mechanics into a deterministic harness and structured backend records. Agents receive concise projections rather than repeatedly reading and rewriting the protocol.

  1. 1. SelectHuman and Orchestrator select one or more fid issues and approve a Work Envelope.
  2. 2. AuthorizeThe kit classifies risk and sets scope, authority, budgets, obligations, protected decisions, and stop conditions.
  3. 3. ExecuteBuilder claims work; the harness enforces transitions and records runs, receipts, evidence, and repository identity in fid.
  4. 4. ReviewReviewer operates only when the risk lane or outcome requires independence; findings and coverage are structured records.
  5. 5. Decidefid generates resume, completion, attention, and Human views from facts; the Human supplies judgment where policy requires it.

The kit's current V2 bootstrap uses one frontier agent per phase without spawning the V1 role set. The eventual Orchestrator, Builder, and Reviewer contracts describe the workflow offered to consuming projects; the Markdown used while building those contracts is V1 scaffolding, not a preview of V2's steady-state artifact cost.

Recommended domain relationship The relationship that removes the apparent contradiction

An Issue says “this work exists” and retains its identity across backlog, execution attempts, deferral, and later follow-up. A Work Envelope says “this selected revision of this work may be executed now under these constraints.” A claim/run says who is attempting it; receipts and evidence say what actually happened. The envelope is neither a replacement issue nor a super-issue.

05 / Boundary contract outcomes

The cross-product contracts are resolved; their roadmap dispositions remain.

Cross-product analysis Six contract resolutions Gates A and B settle the product boundary and detailed semantics. Gate D must now translate those outcomes into explicit roadmap dispositions.

1. Policy lives on both sides of the port

D-006 says the kit owns domain policy, but the V2-2 memory backend applies promotion, obligation-strengthening, budget, attention, claim, and completion rules. A fid adapter implementing the same interface would reproduce kit policy, not merely persist it.

Decision needed: publish shared pure transition semantics, or narrow fid enforcement to generic preconditions and trusted-obligation checks.

2. Both products define the Work Envelope

V2 has an implemented schema and domain model. fid schedules its own Work Envelope for v0.3a. Independent definitions will drift; mapping current issues is not lossless.

Decision needed: the kit owns the semantic schema; fid implements a first-class compatible aggregate and stores project references rather than competing prose.

3. Gate definition ownership is duplicated

fid's draft treats project-owned .fid/gates.toml as the live registry parsed at execution; V2 requires an authored definition to become an immutable registration bound to project, overlay, repository, and authorization identity.

Approved direction: the project owns authored values, the kit owns schema/validation/activation, and fid resolves only immutable active registrations. Exact authoring filename is deferred.

4. Kit Activation risks dual truth

V2-1 already coordinates filesystem activation records while the backend port also models full activation state. fid currently has no activation target.

Decision needed: the kit owns the cross-resource coordinator; fid persists its participant state and shared activation identity, unless one canonical record is explicitly chosen.

5. Two different meanings of export

fid's v0.4d export is a one-way whet-style Markdown projection. V2 requires a lossless, backend-neutral recovery export with identities and history.

Decision needed: portable structured export moves forward; Markdown export becomes an optional projection.

6. Phase 20 solves the old role model

fid plans project-configurable permissions for seven legacy roles. V2 uses Human, Orchestrator, Builder, Reviewer, and harness authority, with policy owned by the kit and Work Envelope.

Approved D1: supersede Phase 20; retain current issue CLI policy for compatibility, defer configurable global roles, and design generic actor/capability enforcement with the port.

Human decision status Gates A, B1-B4d, and C are approved. Gate B4 lifecycle design is complete; Gate D roadmap disposition remains to be worked through.

Gate A / Product - APPROVED 2026-08-08
fid remains the local issue tracker and owns durable operational work state and evidence. The kit owns engineering-workflow policy, risk/authority/role routing, deterministic orchestration, and provider projections. Recorded in ADR-0004.
Gate B1 / Policy and enforcement - APPROVED 2026-08-08
The kit evaluates engineering-workflow policy and compiles the approved Work Envelope. fid does not recalculate risk, routing, or obligation-selection policy; it enforces generic integrity and the recorded envelope's authorization, non-weakening, trusted-evidence, freshness, revision, lease, idempotency, and lifecycle preconditions.
Gate B2 / Trusted executor - APPROVED 2026-08-08
fid is the primary trusted local executor and creates receipts from observed registered-gate execution. External attested runners are a secondary CI/Assured/release extension; reported results never satisfy trusted obligations. Live output is required, with framing still to design.
Gate B3 / Gate Definition authority - APPROVED 2026-08-08
The project owns machine-readable Gate Definition values; the kit owns schema, validation, and activation; fid owns immutable registrations and never executes mutable authoring configuration. Quality-plan prose is explanatory, the exact authoring filename is deferred, and standalone clients use the same registration contract.
Gate B4 / fid-native work identity - APPROVED 2026-08-08
fid Issues and their relationships are the only durable work graph. Work Envelopes reference selected Issues; Claims and Runs bind Issue, Envelope revision, actor role, and optional Obligation; the harness derives noncanonical Next actions. Review uses Review Runs/Records rather than Review Work Items. Gates B4a-B4d resolve the required lifecycle scenarios.
Gate B4a / Parallel Builder isolation - APPROVED 2026-08-08
One Issue permits one active mutating Builder Claim. Parallel mutation requires distinct selected Issues, separate worktrees, and declared provably disjoint scopes; otherwise the second Next action returns mutation-conflict. Read-only Review Runs may coexist, but their results bind the exact repository identity and stale when it changes.
Gate B4b / Interrupted-Run recovery - APPROVED 2026-08-08
Continuation creates a linked new Run and marks the prior Run interrupted; identity is never reused. Recovery requires confirmed executor termination, eligible Claim release/expiry/authorized supersession, and non-destructive worktree reconciliation. Unknown liveness or unsafe state stops; obligations, evidence rules, and consumed budgets carry forward.
Gate B4c / Review rework - APPROVED 2026-08-08
A changes-required Review Record is immutable but leaves the review Obligation unsatisfied. Rework uses a new Builder Run on the original Issue and Envelope; only a new independent Review Record resolves Findings. Target changes stale prior proof, material contract changes require an Envelope revision, and exhausted cycles return review-rework-exhausted plus Attention.
Gate B4d / Multi-Issue Envelope revision - APPROVED 2026-08-08
Partial progress is derived from selected fid Issue states, not persisted as another lifecycle. Contract changes create immutable revisions after old-revision mutation is quiescent. Unfinished removals require an authorized visible disposition; completed Issues remain complete; cancellation does not satisfy completion or dependencies.
Gate C / Scope - APPROVED 2026-08-08
Implement and qualify all twelve V2 backend-port capabilities before migrating a live project. Deliver them through bounded vertical slices with contract and conformance evidence, controlled fixtures, and a disposable migration rehearsal; this does not approve the whole historical fid roadmap or require every task to invoke every capability.
Gate D1 / Phase 20 disposition - APPROVED 2026-08-08
Supersede Phase 20 as written. Preserve V1 issue-CLI permission behavior, fid policy show, and implemented workflow authoring. Defer role_permissions, fid role create, and fid policy set pending standalone dogfood evidence; enforce generic actor/capability and recorded Envelope authority in the backend port.
Gate D / Remaining roadmap disposition
Explicitly dispose the remaining non-port feature groups, then ratify the replacement backend-port vertical-slice order so retired or deferred rows cannot quietly re-enter as presumed scope.
Stop condition

If the joint contract cannot produce a small, comprehensible first production capability set without copying the kit's policy engine into fid, stop and revisit Gate A explicitly. Do not silently revive the rejected kit-native or hybrid persistence options, or preserve both products behind a boundary neither can explain.
