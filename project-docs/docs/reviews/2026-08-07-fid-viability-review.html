01 / Executive answer

There is a useful product inside fid. The current project is not yet evidence of it.

The core idea remains sound: coding agents need durable state across sessions, small machine-readable work items, dependency-aware selection, and evidence that survives chat compaction. fid's local CLI, append-only journal, derived SQLite projection, structured outputs, claims, and workflow checks are a coherent answer to that problem.

The uncomfortable part is that fid has mostly been validated as software, not as a useful tool. Its own charter required v0.1 to replace roughly 70% of daily interaction with the existing Markdown workflow before v0.2 began. That did not happen in any sustained, observable way. The build continued into v0.2 while fid itself remained on the Markdown pipeline it was supposed to replace.

The project passed the wrong test.

It proved that fid behaves according to an unusually detailed specification. It has not proved that using fid is cheaper, clearer, or more reliable than a lean prompt, tests, git history, and a small task file. That is the decision-critical gap.

Continue

Preserve the code and run a bounded product experiment. The foundation is too good to discard without testing the real workflow, and the trusted-evidence direction targets a genuine failure seen in the project.

Do not continue as planned

Do not start another heavy phase, expand the entity graph, or polish configurable roles before proving daily use. More specification and more workflow controls would compound the exact cost the product is meant to remove.

The product is between layers.

Today fid is a well-built local issue tracker with workflow controls. The roadmap's strongest answer to process theatre, trusted evidence plus lean completion, is still future work. The existing build process therefore pays the old prose costs without receiving the planned automation benefit.

04 / Product thesis

The durable-state thesis survives. The full knowledge-graph thesis is unproven.

Load-bearing value

  • Durable work stateAgents still lose coherence across long sessions and context resets.
  • Executable selectionA deterministic ready queue is cheaper and safer than asking a model to reconstruct priority and blockers.
  • Trusted evidenceThe repository already experienced false gate claims. Executed receipts solve a real failure.
  • Local and inspectableA single binary and queryable local state remain attractive for private solo work.

Speculative value

  • Deep role modelSeven roles and configurable permissions may encode this one workflow more than a general user need.
  • Full QA ontologyReviews, plans, findings, assertions, outcomes, and retrospectives as separate entities are not yet justified by saved effort.
  • Universal knowledge graphStructured metadata helps queries, but excessive normalization can turn ordinary reasoning into data entry.
  • Broad output surfaceFour formats for every read command increase compatibility and test cost before daily utility is established.

The best product framing is narrower than the charter's eventual "standard storage/query layer" ambition: a local evidence-backed work ledger for coding agents. That framing keeps task state, ready selection, claims, completion, receipts, and a small decision trail. It does not require fid to model every artifact an engineering process can produce.

Large test volume is not itself waste; journal replay, migrations, and CLI contracts deserve strong tests. The warning is the ratio of workflow artifacts to observed product learning. Phase 19's own closeout says all eight escalations were in verification apparatus or evidence records, including four in a shell ceremony later replaced by one standing Go test. The earlier retrospective similarly found false claims and identifiers consuming multiple stop/resume cycles.

The early dogfood criterion is not demonstrated as written.

The charter and roadmap require fid to replace about 70% of daily Markdown interaction and to be used for real project work before v0.2. The Phase 17 checklist records five passes with "n/a" notes. The only fid workspace visible in git history contained seven synthetic issue-creation events and was removed; the repository now ignores /.fid/. Phase 19 human validation used a disposable scratch workspace. Those are valid feature checks, not evidence of sustained adoption or reduced cost.

06 / Engineering quality

The codebase is a reason to test the pivot, not a reason to keep funding it.

Current deterministic state is healthy.

On 7 August 2026: gofmt -l cmd internal returned no files, golangci-lint run ./... returned 0 issues., go test -race ./... passed, the CLI built, and refreshed statement coverage was 77.0%.

What is architecturally sound

  • The journal-canonical, projection-derived design is understandable and tested. It gives inspectable git history without committing a SQLite binary.
  • Domain packages are recognizable and the CLI is mostly a thin adapter over them.
  • Rejection-before-append and rebuild parity are appropriate invariants for an agent-mutated ledger.
  • The dependency set is restrained for the problem: Cobra, migrations, pure-Go SQLite, YAML, and test utilities.

What will become expensive

  • Most domain packages know about config, DB, journal, and policy orchestration. New entity families repeat a substantial write-path protocol.
  • internal/format imports nearly every read-domain package, so adding entities multiplies renderer and compatibility work.
  • Several production files already exceed the project's 400-line target, including internal/sqlquery/sqlquery.go at 595 lines and issue files at 412-464 lines.
  • The root README still says "Pre-implementation" even though v0.1 is tagged and v0.2 work exists. Product-facing basics lost priority to internal workflow precision.

None of these are stop-level defects. They do mean every new entity or output format is costlier than its roadmap row suggests. The correct response is to narrow the product, not launch a refactoring phase before value is proven.

07 / Current model practice

Current guidance supports durable state and strongly argues for less scaffolding.

Current evidence Implication for fid
OpenAI's current model guidance says to state instructions once, expose only relevant tools, keep prompts lean, and validate changes on representative evals. Its internal coding-agent sample found leaner system prompts improved scores while materially reducing tokens and cost. fid's 9,000-plus words of default project context, before task and role material, should be treated as a performance hypothesis to ablate, not safety infrastructure to preserve by default.
Anthropic still recommends incremental work and structured artifacts for long-running tasks, but its 2026 harness work removed context resets when a stronger model no longer needed them and warns that harness assumptions go stale. Small task state and handoffs remain useful. Fixed six-role ceremonies, mandatory reports, and phase-wide context should survive only when an ablation shows they improve outcomes.
A 2026 empirical study found repository context files tended to increase inference cost by more than 20% without significantly improving task completion; its recommendation is minimal, required human-written instructions. The current workflow is likely paying real recurring context cost. fid should retrieve precise state just in time and remove duplicated instruction text.
Productivity evidence is moving quickly and remains uncertain. METR's early-2025 study measured a 19% slowdown for experienced maintainers, while its 2026 update says newer tools likely improve outcomes but the new estimate is selection-biased and unreliable. Self-reported speed is not enough. fid needs its own measured baseline against real tasks, including human attention, tokens, retries, and elapsed time.
DORA's 2025 research describes AI as an amplifier of an organization's existing strengths and dysfunctions. Encoding a good minimal workflow can help. Encoding ceremonial dysfunction makes agents produce that ceremony faster and at larger volume.

This is not an argument for "let the model handle everything." It is an argument for deterministic code around facts and constraints, short context around judgment. That principle is much closer to fid's evidence-foundation direction than to its current Markdown build pipeline.

08 / Competitive reset

The landscape assessment is already strategically stale.

The charter says Beads is general-purpose task tracking without agent-specific concerns. The current Beads repository describes itself as a distributed graph issue tracker for AI agents and persistent structured memory replacing Markdown plans. It shows more than 10,000 commits and roughly 1,800 forks. It is now a direct competitor, not an adjacent inspiration.

kata is another direct 2026 entrant: a Go-based local task ledger for coding agents with create, claim, relate, close-with-evidence, JSON/agent output, a TUI, event history, and an explicit comparison against hosted trackers. OpenSymphony goes further into task graphs, isolated workspaces, harness execution, recovery, and knowledge capture.

Position Where others are ahead Possible fid edge
Agent task ledger Beads and kata have clearer current positioning, active ecosystems, and human surfaces. No-daemon, git-journal-canonical operation may remain attractive.
Workflow engine Configurable workflows are common and not a compelling wedge on their own. Schema-enforced completion obligations could be stronger if they stay simple.
Evidence kata already attaches evidence to close operations; CI platforms record test runs. Trusted local receipts, tree freshness, and no fabricated pass form a coherent differentiated bundle.
Orchestration Current tools already connect tasks, worktrees, agents, review, and recovery. fid should integrate through a small CLI contract, not try to become the orchestrator.
Competition changes the bar, not necessarily the personal decision.

fid has no monetization goal, so it need not win a market. It does need to beat installing an existing tool plus a small custom skill. A bake-off is now cheaper and more informative than another implementation phase.

09 / Recommendation

Pause, validate, then choose one of three paths.

Continue

Evidence-led fid

Choose this only if real use beats alternatives. Skip broad governance work. Build trusted gate receipts and lean completion, then remeasure.

Pivot

Focused companion

If another tracker wins task management but fid's evidence model is valuable, narrow fid to a local completion/evidence ledger or contribute that capability upstream.

Stop

Archive cleanly

If fid is not voluntarily used, does not save time, and catches no unique problems, tag the current state, write a short retrospective, and stop spending tokens on it.

My expected outcome

The most likely good outcome is a narrower fid: defaults rather than a general role/workflow platform, a compact task and decision ledger, and trusted completion evidence. The most likely bad outcome is continuing through v0.3/v0.4 to model the existing process in full before learning whether the process deserves to exist. Avoid that path.

10 / Validation plan

A ten-task bake-off, not another phase.

Freeze the roadmap

No Phase 20 implementation, schema design, or spec expansion during the experiment.

Select ten real tasks

Use work you would do anyway: a mix of bugs, small features, refactors, and one cross-cutting change. No synthetic validation tasks.

Use three conditions

Run roughly four tasks with fid, three with Beads or kata, and three with a minimal Markdown baseline. Match task shape as closely as practical.

Use light process only

One task contract, tests, and a short result. No validation contract, mid-phase review, completion report, or role fan-out unless risk specifically requires it.

Measure automatically where possible

Record elapsed time, agent tokens/cost, human-active minutes, commands, retries, context resets, defects found, and artifacts authored. Unknown stays unknown.

Ask the adoption question

After each task: would you voluntarily use this condition for the next task if no experiment required it? Record yes/no before looking at totals.

Pre-committed thresholds

Signal Continue threshold Stop or pivot trigger
Voluntary preference fid chosen for at least 3 of its 4 follow-up decisions fid chosen once or never
Human bookkeeping Median under 5 minutes per task and at least 25% below baseline Equal to or worse than baseline
Agent cost No more than 10% token overhead unless offset by a clear quality gain More than 20% overhead without unique value
Artifact volume At least 70% fewer hand-authored workflow words than the current phase process New duplicate state or mandatory prose
Unique value At least two useful invariant/evidence catches or three recurring queries made materially easier Everything useful already supplied by tests, git, or the alternative tracker
Recovery A fresh agent resumes correctly from fid state without reading a phase archive It still needs the same Markdown corpus to understand the task

The sample is small and will not produce publishable statistics. It is sufficient for the actual decision: whether this solo developer should spend more evenings and tokens on this tool.

11 / Scope disposition

Keep the foundation. Pause the platform. Delete ceremony from the plan.

Disposition Capability Reason
Keep Journal, rebuild, migrations, maintenance Distinctive, robust local persistence foundation.
Keep Issues, ACs, ready queue, claims, concerns, simple transitions Forms the minimum useful work ledger and supports the experiment now.
Next if proven Trusted receipts, evidence freshness, lean completion Directly addresses false gate claims and mandatory prose costs observed in the project.
Pause Phase 20 role/permission configurability Low near-term value for the primary solo-user case; custom workflows are not the wedge.
Pause Governance entities, reports, context packs, TUI Potentially useful, but only after the core workflow is voluntarily adopted.
Drop unless measured Heavy mode as default, 70-row contracts, report-per-task, routine multi-role fan-out Current evidence shows high cost and late catches concentrated in the evidence apparatus itself.
Drop "Standard storage layer" ambition as a planning driver Too broad for an unproven solo tool in a fast-moving competitive category.

12 / Immediate next steps

What I would do next, in order.

  1. Close Phase 19 administratively in one short commit. Do not run a deep retrospective first; this report already captures the decision-level learning.
  2. Correct the public basics. Update the stale README status and add an actual install/quickstart. This is a small credibility check, not a product phase.
  3. Create a real .fid/ workspace for fid or another active project. Use it as the only structured task state during the experiment; do not mirror every row into phase Markdown.
  4. Install one competitor. Beads is the closest architecture/thesis comparison; kata is the clearest task-plus-evidence comparison.
  5. Shrink agent context for the experiment. Keep hard safety, architecture, and exact gate commands. Remove duplicated process instructions and retrieve detailed specs only when a task needs them.
  6. Run the ten tasks and decide. The decision is made from observed preference, time, cost, recovery, and unique catches. No threshold should be renegotiated because the existing code is substantial.
The next useful artifact is data, not another specification.

A one-page experiment ledger with ten rows will answer more about fid's future than the next 10,000 lines of roadmap, validation, review, or workflow documentation.

Limitations

This was a repository and market review, not a controlled productivity study. Historical token spend and human time are not available in a trustworthy complete form, so process cost is inferred from observable artifact volume, workflow incidents, and the absence of sustained dogfood data. Competitor descriptions are based on current primary project pages, not a full hands-on migration. The report intentionally did not inspect held-out scenarios.

Bottom line: fid is worth one honest product experiment, not another faith-based phase. Preserve the strong code, remove the ceremony, measure daily use, and let the result decide.
