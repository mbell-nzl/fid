1. Executive summary for the reader

The strongest shared lesson is to make work easy to verify and cheap to resume. Agents can now do much more implementation, but the field has not established one winning development method—or shown that more agents, more plans or more generated code reliably means better software.

  1. Put repeatable knowledge in small skills; put obligations in executable controls. A prompt can describe a rule. A trusted runner, CI check or correctly configured hook can enforce it. These are different jobs. Evidence →
  2. Subagents are useful boundaries, not promotions. Fresh-context review, isolated exploration and separable parallel tasks justify them. A sequence of impressive role titles does not establish independent judgment. Evidence →
  3. Use predictable control flow where the next step is already known. Let models solve problems inside it. Large exploratory swarms remain a legitimate alternative, with substantial coordination costs. Evidence →
  4. Keep durable state outside the conversation. Git, concise files and task stores all work; the important properties are recoverability, clear ownership and an authoritative answer to “what next?” Evidence →
  5. Planning is not obsolete. The debate is about proportionality and maintenance. Heavy methods are adding small-change paths; sophisticated vendor playbooks still retain explicit specs. Evidence →
  6. “Done” needs an observable meaning. Tests, real application behavior, review resolution and required approvals should refer to the actual delivered revision. Green tests cannot establish that the intended problem was solved. Evidence →
  7. Receipts address a real gap. Execution logs and attestations exist, but portable, trusted acceptance evidence for coding agents is not yet a settled standard. A signed claim can still be false. Evidence →
  8. Review is becoming a capacity constraint. Agent review helps triage; it does not remove the need to assess intent, risky decisions and whether findings were resolved. Cross-model review is plausible, not conclusively superior. Evidence →
  9. Productivity results are heterogeneous. Controlled trials, surveys, internal case studies and PR statistics answer different questions. Measure human attention, rework and escaped defects alongside throughput. Evidence →
  10. Portability is improving fastest in content formats. Skills, repository instructions and MCP reduce duplication; permissions, hooks and completion semantics still vary by host. Evidence →

Increasingly standard in the surveyed ecosystem: repository guidance, reusable skills, executable feedback, isolated workspaces, external task state and explicit human control. Losing favor in guidance: giant always-loaded instruction files, blind one-shot completion and permanent scaffolding whose benefit is never measured. There is no adoption census proving that role personas or formal specifications have disappeared.

Five ideas worth testing against the revised plans: a small skill library; one reviewer with separate context and restricted tools; a bounded deterministic loop; revision-bound execution records; and a compact human queue for decisions and unresolved findings. Treat these as a coherent experiment, not a proven package. Compare human minutes and defect escape before adding ceremony.

3. Findings by research question

“Consensus” here means convergence among the cited guidance, not a representative survey of engineers. Confidence in a documented capability is separate from confidence that it improves outcomes.

3.1 Skills vs subagents vs role personas

Convergence: encode reusable procedures as focused, discoverable knowledge; isolate work when a separate context or tool boundary is useful. Alternatives and dissent: Superpowers uses implementer and review stages; Cursor retains planners and workers. Neither supports the blanket claim that roles are an anti-pattern. [E22] [O7]

Assessment: a persona is merely wording until it changes inputs, permissions, ownership or evaluation. Reviewer independence is better expressed by access to requirements and the diff, with no obligation to defend the implementation, than by a “senior QA” title. Evidence is strong for capability, moderate for practical utility and weak for a universal optimal agent count. A single reviewer is a reasonable baseline to evaluate, not a scientifically established optimum.

3.2 Orchestration and unattended execution

Convergence: long runs need a bounded scope, feedback, durable checkpoints and a recovery policy. Alternatives: a shell loop is economical for a linear task; a durable workflow engine handles outages and suspended approvals; an LLM planner can discover work whose decomposition is not known beforehand. [A1] [O9]

Unattended acceptance checklist, synthesized: choose ready work atomically; identify its workspace; set time, cost and retry budgets; run independent checks; retain failures; park repeated failures; stop on protected decisions; reconcile after interruption; validate the merged result. Worktrees prevent filesystem collisions, not semantic conflicts. Retrying is safe only if effects are repeatable or recorded. Evidence favors these engineering properties; comparative proof that one orchestrator dominates is thin.

3.3 Durable state across sessions

Convergence: conversation history is insufficient as the only work record. Alternatives: Markdown offers legibility and git history; an issue tracker offers collaboration and existing ownership; purpose-built stores offer dependency queries and compact machine interfaces. Current tools span all three. Tracker evidence [O11]

Assessment: agents use state well when retrieving the next relevant item is easy, updates are unambiguous and reality can be reconciled with the record. File-versus-database is less decisive than duplicate authority. Store prose once, link it from structured state, and distinguish “claimed,” “running,” “blocked,” “checked” and “accepted” where those distinctions affect action. These are design inferences, not a proven universal schema. No controlled evidence here establishes that a particular tracker improves defect rates.

3.4 Planning artifacts and agent waterfall

No consensus on artifact volume. Explicit plans remain common; the disagreement is whether specifications are disposable scaffolding, maintained documentation or executable source. The Fowler-site analysis makes those distinctions useful. Anthropic’s current playbook remains structured, while several methods offer quick paths. Planning evidence and critique [A5]

Author’s interpretation: the healthy unit is a decision-bearing artifact. A plan earns its upkeep when it resolves ambiguity, coordinates dependencies or states acceptance. Repeated status prose and copied validation tables often do none of these. Keep stable requirements with the repository or task, transient execution detail with the run, and decisions where later work can discover them. Evidence is mainly practitioner experience; no credible word-count threshold emerged.

3.5 Validation, acceptance and test-first work

Convergence: explicit expected behavior plus executable feedback beats a vague request to “make it production ready.” Test-first practice is prominent in Pocock and Superpowers; pstack emphasizes checking the actual application. [E12] [E4]

Alternatives: unit TDD, acceptance-first examples, property tests, browser journeys, static analysis and held-out evals address different failure classes. A validation contract can be a short mapping from requirement to check, not necessarily a separate bureaucracy. Limits: generated tests can restate generated mistakes; passing visible checks can reward narrow solutions. Preserve independent or hidden evaluation where useful. Evidence supports fast feedback as a practical method, but the survey does not establish an agent-specific causal quality uplift for mandatory red/green on every change.

3.6 Verification of agent claims

Convergence: inspect execution evidence, not an agent’s assurance. Existing verification skills demand fresh checks; host hooks and CI can make checks mandatory. Their trust levels differ. [E21] [A7] [O5]

Assessment: a useful receipt connects a subject revision, check definition, environment, issuer, start and completion, real termination and retained output. A check of dirty files cannot honestly attest only to HEAD. Code changes after review invalidate or narrow the review’s coverage. Append-only history provides auditability; independent execution and protected signing provide stronger resistance to forgery. Supply-chain standards inform the structure without proving test adequacy. No broadly accepted cross-agent “done receipt” standard was verified. Provenance evidence

3.7 Review and finding resolution

Convergence: review is a separate activity from generation; actionable findings should feed back into implementation. Alternatives: fresh same-model context, another model, multiple specialist reviews, managed PR review, and selective human inspection. [E16] Review tools and studies

Assessment: “independent” needs a definition. Fresh context removes one source of anchoring; a different model may diversify errors but shares training patterns and may be weaker. Require concrete location, failure condition, severity and a disposition; recheck the fix, and retain accepted-risk decisions. Measure useful confirmed findings and escaped defects rather than comment counts. Vendor benchmarks support investigating these tools, but do not prove that cross-model review replaces human judgment.

3.8 Human intervention, drop-in control and risk lanes

Convergence: humans retain intent and authority over consequential decisions; automation benefits from fewer routine interruptions. Alternatives: approval at each tool boundary, at a plan, at a risky action or at merge. Risk vocabulary exists, but Routine/Standard/Assured is not a verified industry taxonomy. [O14] [A5]

Assessment: interruption should present the decision, concrete proposed change, evidence and consequence—not a transcript to decode. Drop-in control needs current task and revision, pause/resume/cancel, visible pending actions and explicit takeover ownership. Treat risk as changeable when scope expands. A lane that only adds more prose is unlikely to help; a lane that changes required evidence or authority is operationally meaningful. Evidence is moderate engineering guidance; optimal approval frequency is unsettled.

3.9 Quality outcomes

Measured evidence is mixed and task-dependent. Controlled coding-assistant gains and METR’s slowdown result are compatible because participants, tasks and tools differ. DORA describes organizational associations, not a randomized method comparison. Later studies add throughput and review-load evidence but do not settle lifetime maintenance cost. Study table and limitations

Assessment: small reviewable changes, reliable environments, checks that detect real failures and independent acceptance have strong engineering rationale and repeated practitioner support. There is weaker direct causal evidence isolating each in modern agent workflows. Star counts, generated lines, successful demos and benchmark scores cannot establish production quality. Notable dissent includes OpenAI’s willingness to accept fewer blocking gates when correction is cheap; that tradeoff should not be generalized to irreversible data or security decisions. [O6]

3.10 Measurement

Convergence: throughput alone is inadequate. Alternatives: delivery metrics, task completion evals, cost accounting, review sampling and human time diaries. Self-reported productivity is useful as experience data, not a substitute for observed outcomes. Measured evidence

Suggested comparison protocol, author’s synthesis: compare similar task classes; record model/harness version and risk; measure elapsed time and active human minutes separately; add token and runner costs; count repair cycles, reopened work, review findings confirmed and defects escaping over a fixed follow-up window. Report failed and abandoned attempts. Prefer cost per accepted change to tokens per response. Track documentation-maintenance minutes explicitly to detect agent waterfall. There is no validated universal score combining these dimensions.

3.11 Portability across providers

Convergence: portable knowledge is increasingly feasible through skills and repository files. Alternatives: one canonical source with generated host adapters; a host-neutral CLI; or a shared orchestration runtime. [A12] [O3]

Assessment: separate the procedure from tool names, environment setup and permission semantics. Test discovery, explicit invocation, reviewer isolation, command failures and cancellation in every supported host. MCP supplies connectivity rather than identical policy. Plugin marketplaces do not certify equivalent behavior or safety. Evidence is high for format availability and moderate for practical portability; an identical file is not proof of identical execution.

3.12 Trends and direction

Observed direction: the surveyed 2026 sources emphasize harnesses, reusable skills, durable execution and human attention; methods are converging on mixed deterministic and model-driven components. This is a synthesis of dated publications, not an adoption time series. [A4] [O8]

Contested: how much planning survives stronger models, whether review becomes automated acceptance, and whether small loops or adaptive hierarchies scale best. Forecast, low confidence: execution evidence and review state will become more structured; portable skills will coexist with host-specific enforcement; methods will need frequent simplification as models improve. None implies that autonomous code volume removes engineering responsibility.

4. Source and method deep dives

Anthropic: a family of methods, not one prescribed process

Identification verified. The relevant sources include the 2026 agentic coding trends report, which explicitly labels an “Agentic SDLC,” and Louis Claxton’s August 21, 2026 AI-native SDLC playbook. The former is a vendor outlook: its compressed cycle-time diagram is a prediction/illustration, not a controlled measurement. It describes humans choosing direction and reviewing outcomes while agents implement, test and document. The latter is a concrete operational playbook. They should not be conflated with a universal engineering standard. [A16][A5]

The playbook preserves an approved chain of intent.md → spec.md → plan.md, with policy concerns escalated to their owners. It distinguishes the developer’s continuous feedback loop from a final fresh-context verifier, asks for reproducible checks, protects tests during bug fixes, and uses review policy, CI, transcripts and observability. It pairs throughput measures with rework. Strength: accountability remains visible as implementation accelerates. Weakness, by inference: applying the full artifact sequence to every small change could reproduce the reader’s agent-waterfall problem. Its existence is important dissent from the claim that the field has abandoned written plans or human approval before coding. [A5]

Simple composition and context economics

Building effective agents (December 19, 2024) separates predefined workflows from agents that decide their next steps. Its recommendation is to add complexity only when needed; workflows buy predictability, while agents buy flexibility at additional cost and latency. Routing, parallel work, orchestrator/workers and evaluator/optimizer are patterns to choose among, not mandatory organizational roles. Frameworks can obscure the underlying interactions. The current page explicitly warns that tooling has evolved since publication and points to Managed Agents. Evidence: vendor engineering experience across customers, not a comparative trial of development methodologies. This supports a deterministic outer loop for stable transitions while leaving exploration and implementation decisions to the model; it does not prove scripts always outperform model orchestration. [A1]

The September 2025 context-engineering article treats context as a limited resource. Relevant instructions, retrieval, compaction, external notes and isolated subagent exploration all help. Compacting too aggressively can discard facts whose significance emerges later. Persistent notes let new contexts recover goals and decisions, while subagents keep large searches out of the main conversation. Practical implication: a small authoritative state record and navigable repository can matter more than a long persona prompt. Its recommendations are engineering observations, and model-specific details should not be frozen into permanent policy. [A2]

Long-running harnesses: continuity, verification, and deleting obsolete machinery

The November 2025 harness article starts with a common failure: a model tries too much, leaves a broken environment, or declares success prematurely. Its initializer prepares a feature list and environment; later sessions take one feature, inspect git and progress notes, test end-to-end, and leave a useful checkpoint. The team found JSON feature status less prone to accidental rewriting than Markdown. Browser testing caught failures missed by unit tests or HTTP requests. Limit: instructions against editing tests are still instructions; an agent-maintained passes field is not independently verified evidence. This is a credible worked example for resumable work, not proof that every project needs hundreds of predefined features. [A3]

Prithvi Rajasekaran’s March 2026 follow-up used planner, generator and evaluator agents, with concrete evaluation criteria and structured handoffs. One demonstration compared a 20-minute, $9 solo run with a six-hour, $200 harness run; better output cost much more. With a stronger model, some sprint scaffolding became unnecessary: an evaluator helped most near the model’s capability boundary. In a later DAW example, QA caught core functionality that was merely displayed or stubbed. Lesson: evaluate the marginal value of each reviewer and handoff against the current model. Evidence quality: useful vendor case studies, small selected examples, no broad causal estimate. This is unusually direct evidence against making a fixed role bureaucracy permanent. [A4]

Current Claude Code guidance: knowledge versus enforcement

The living best-practices page explicitly distinguishes non-deterministic instructions (prompts, CLAUDE.md, skills) from harness-enforced controls (hooks, deny rules, sandbox and managed settings). It recommends short project guidance and says subagents earn their cost through parallel independent work, context isolation, restricted tools, or a reviewer who did not see implementation. Unattended work needs a definition of done, a check, an allowed scope, a stopping budget, and a destination with final approval. Confidence: high about the documented product behavior; moderate about general quality benefits, because these are vendor recommendations. The guidance supports a compact skill plus independent reviewer, but a skill alone cannot enforce completion. [A6]

Subagents have their own configuration, tools, permission settings and context. The documented use cases include high-volume exploration, parallel research and chained tasks; foreground and background operation are available. Defining a reviewer with read-only tools gives a meaningful operational boundary. Merely naming the same unrestricted agent “QA” does not. Fresh context reduces contamination by the author’s narrative; it does not make two instances of the same model statistically independent. That last distinction is this survey’s inference, not a product guarantee. [A8]

Hook traps matter for receipts. The hooks reference documents event-specific blocking. Exit code 2 blocks eligible events; a conventional exit 1 can be non-blocking. A timed-out hook may render no decision unless failure blocking is configured. A background process printing a rejection after the hook exits cannot retroactively stop the action. Current documentation exposes onFailure: "block" for applicable hooks. Therefore “a hook exists” is weaker than “the required check ran, terminated, failed closed, and bound its result to this revision.” Test timeout, missing executable, malformed output and bypass paths as part of the control. The final recommendation is an inference from the documented behavior. [A7]

Skills, plugins, marketplaces and programmable execution

Skills launched October 16, 2025; the announcement records the open-standard update on December 18, 2025. The standard specifies a directory with SKILL.md, YAML metadata including name and description, and optional scripts, references and assets. Compatibility metadata can declare environmental requirements. It standardizes a portable knowledge package, not scheduler semantics, permissions or proof of execution. [A14][A12]

The official anthropics/skills repository is verified. GitHub’s detailed repository panel displayed 184.6k stars, rounded, observed October 29, 2026; its header rounded further to 185k. These are interest signals, not installations or demonstrated engineering outcomes. The repository distinguishes Anthropic’s skill implementations from the open specification and includes a skill template and plugin packaging. Useful as a reference implementation and examples; individual skill licenses and assumptions still need checking. [A13]

A Claude Code plugin bundles skills, agents, hooks, MCP servers and other components into one installable unit. A marketplace is a catalog locating such packages, not a separate method or a quality certification. This is a natural distribution mechanism for a small engineering kit; provider-specific hooks and agent configuration remain outside the portable skill format. [A9]

Headless execution is documented as claude -p, with structured output and tool allowances; the Agent SDK provides the Claude Code agent loop and tools in Python and TypeScript, including approvals, hooks, sessions, observability and cost tracking. Shell loops and programmatic orchestration are therefore supported first-class options. Tradeoff: scripting keeps stable state transitions inspectable; the SDK helps when richer permission handling or session control justifies a program. Neither turns a model’s final success message into an independent test result. [A10][A11]

Internal practices and outcomes: useful, unusually favorable, not universal

Anthropic’s December 2025 study surveyed 132 engineers and researchers, interviewed 53, and analyzed internal usage. Respondents reported using Claude in 59% of their work and a 50% productivity increase, compared with recalled 28% and 20% a year earlier. The article also mentions a 67% increase in merged PRs per engineer per day. These are different measures: self-reported productivity and observational throughput, neither a randomized causal estimate or direct quality measure. Staff described expanding into unfamiliar technical work, clearing neglected small improvements, and reserving difficult organizational judgment for humans. The paper itself discusses measurement limitations and contrasts METR’s findings. [A15]

The October 16, 2026 internal study extends the picture using employment, usage, output and organizational data plus 17 interviews. It reports interactive agent hours six times employee hours by August and identifies human attention as the limiting resource. Employees build visibility and monitoring systems to manage agent output. Relevance: work ledgers and review queues address a real reported operational need. Caution: frontier-lab tooling, talent, incentives and task mix are atypical; more output is not proof of fewer defects or a sustainable review load. [A17]

Anthropic’s frontier-lab measurement proposal is also relevant beyond coding: measure oversight and intervention, not only output. It proposes metrics for the extent of AI-led R&D, monitoring of agent activity, and resource allocation, with independent verification as an explicit goal. For a personal workflow, the transferable idea is to track the coverage and responsiveness of oversight rather than equate agent hours with progress. This is an analogy, not evidence that the proposed fid receipt format already has industry-standard adoption. [A18]

pstack: Lauren Tan’s engineering workflow, plus the naming collisions

Identification: high confidence. The most likely intended source is cursor/plugins/pstack, authored by Lauren Tan, known as poteto. This is a skills-and-playbooks system used by its author at Cursor, with multi-model work and verification central to its approach. It is not Garry Tan’s gstack. Nor is it the Unix process-stack inspection command. Because the original lives inside a plugin collection, that repository’s stars cannot measure pstack’s individual adoption. [E1]

What is distinctive: the entry point, poteto-mode, routes a task into an appropriate playbook rather than asking the human to memorize the entire skill catalog. It emphasizes understanding an unfamiliar system, describing the data model before coding, and using parallel design exploration when a boundary needs design. Observable questions should be settled by an experiment; product preferences remain human decisions. This is a judgment-heavy orchestration method, not evidence that LLM orchestration has disappeared. [E2]

The arena skill runs multiple candidate attempts, chooses a base, incorporates useful ideas from alternatives, and verifies the combined result. This is distinct from splitting independent tasks across workers: it buys alternative designs at additional token and evaluation cost. Assessment: useful where an early structural choice is expensive to reverse; wasteful when the answer is already mechanically determined. Agreement among candidates does not establish correctness. [E5]

The closest fit to the proposed work ledger

show-me-your-work maintains one append-only TSV decision log. Rows contain timestamp, workstream, decision, reason, evidence pointer and result; a changed decision adds another row rather than rewriting history. Evidence points to commits, PRs, source locations or artifacts rather than expanding into paragraphs. It logs meaningful checkpoints, not every keystroke, and keeps the log local unless review justifies committing it. The inspected version also distinguishes a new run’s entries from inherited rows. Assessment: this is unusually close to a lightweight receipt trail, but an agent-authored TSV is not a cryptographic attestation or proof that a claimed command executed. [E3]

create-verification-skill generates a project-specific way to launch, drive and observe the real application. It starts by discovering the actual user surface and existing harness, including CLI/PTY and HTTP options. Readiness means usable with migrations and seed data, not merely a responsive port. Evidence should include actions and resulting side effects, and survive cleanup. Assessment: this goes beyond “the unit suite is green” without requiring every project to adopt the same browser-testing stack. It is especially relevant to fid’s CLI and persistent journal behavior. [E4]

Unattended use: the overnight guide asks for a checkable finish condition, isolated worktree, permissions and an escape hatch. Trust is earned through supervised runs, usable observation tools, stage-level verification and inspecting failures. Its loop checks the goal, makes a small justified change, verifies, keeps or discards it, then logs the decision. Its morning audit uses a reviewer from another model family and highlights decisions requiring human attention. Assessment: this combines a mechanical wake-up mechanism with LLM judgment; the desired property is inspectable progress, not simply more hours running. [E6]

Strengths: concrete verification tools; concise evidence pointers; explicit distinctions between investigation, design, implementation and audit; human catch-up UX. Weaknesses: broad trigger rules and multi-model panels can create substantial overhead; portability depends on actual tools and orchestration, not just copying Markdown; verification still needs a trusted execution boundary. Evidence quality: directly inspectable implementation guidance and author-reported real use, with no controlled comparison establishing a quality advantage over a smaller workflow.

Other pstack projects: phthomas/pstack is a different, Markdown-only spec workflow with eleven ps- skills, fresh-context builders, mechanical gates before review and risk-weighted judges. It resolves optional providers such as ECC, and supports several harnesses through shared skill files. It had 2 stars when observed. It deserves coverage because it also directly matches the brief’s phrasing, but its tiny public footprint does not make it representative. [E7] backnotprop/pstack is a standalone mirror of Tan’s project; finografic/pstack explicitly removes Cursor-specific machinery for portability. Those ports should not be conflated with upstream or have their adoption added together. [E8] [E9]

Matt Pocock: small skills, domain language and behavior-first implementation

mattpocock/skills is the verified repository. The inspected README supports multiple harnesses and asks setup questions about issue tracking, triage labels and document locations. Its response to agent verbosity is shared domain language and recorded design decisions, rather than ever-longer instructions. Its public repository displayed approximately 305.8k stars on observation. These are attention signals, not an estimate of production installations. [E10]

Pocock’s April 27 article describes composing domain clarification, a PRD, independently grabbable vertical slices and TDD. It argues for small skills whose instructions remain readable and editable. Assessment: the principle is modular engineering practice; the specific command vocabulary has evolved, so older posts and current repository names should not be treated as one frozen API. The current grill-with-docs wrapper simply composes grilling and domain-modeling skills. [E11] [E13]

The August 24 TDD guide requires an agreed observable boundary before testing, then one failing behavior and enough code to satisfy it. It explicitly identifies a gap for configuration, wiring, type annotations and plain delegation: forcing TDD there can produce tests that merely restate implementation. Böckeler's critique: specification has three different meanings

Birgitta Böckeler's October 15, 2025 article on Martin Fowler's site distinguishes spec-first (write intent before implementation), spec-anchored (maintain it during evolution), and spec-as-source (humans edit specs rather than code). These should not be treated as one empirical claim. Her hands-on critique identifies review overload, unclear separation of functional intent from implementation, and uncertainty about the maintenance strategy. She connects spec-as-source to earlier model-driven development: replacing deterministic generators with LLMs may remove constraints while introducing nondeterminism. She still finds writing a thoughtful spec valuable. [M8]

Evidence: respected practitioner evaluation, not a controlled comparison. Implication: the strongest agreement concerns making intent explicit; consensus is much weaker on keeping extensive generated documents or treating natural-language specifications as the exclusive source of truth. Current lighter paths in Kiro and BMad are consistent with this critique, though they do not prove it caused those changes.

Practitioners: Willison, Beck and Thoughtworks

Simon Willison makes execution and verification central to agentic engineering. His red/green TDD guidance asks agents to create a failing test, verify the failure, implement, then verify success. This makes the feedback target concrete and helps catch unused or nonfunctional code. It is experienced-practitioner guidance, not an agent-specific controlled trial. Its strength is a small, portable instruction with an observable consequence; its weakness is that an inadequate test can pass while the feature remains wrong. The practical extension is review of test intent and some independent acceptance checks. V12

Kent Beck’s “augmented coding” preserves design judgment rather than treating generated output as the whole job. His May 2025 exploration essay distinguishes rapid hypothesis testing from the predictability required in expansion and extraction; Augmented Coding & Design frames the danger of consuming the design capital that later changes depend on. These are practitioner reflections, not measurements of current model ceilings. They challenge the inference that cheap code makes design investment dispensable. They also warn against heavy planning that prevents exploration: the right artifact depends on whether the work is discovery or production. V13 V14

Thoughtworks Technology Radar, April 2026 describes harnesses as both preparation before action and feedback afterward. It identifies skills and some spec-driven frameworks as useful preparation; compilers, linters, tests, mutation testing and fuzzing provide feedback for correction before human review. This is credible multi-team practice, still opinionated selection rather than an experiment. It supports strong executable controls without requiring a large simulated engineering organization. Its emphasis on architectural drift goes beyond “all tests pass”: architectural constraints may need their own checks and human judgment. V15

AI code review: coverage, independence and remaining uncertainty

Claude Code Review, announced March 9, 2026, runs parallel bug-finding agents, verifies candidate findings and ranks severity, producing a summary and inline comments. Anthropic reported substantive comments on 54% of its PRs versus 16% before and roughly 20-minute average reviews. It explicitly retained human PR approval. These are vendor internal results: comment coverage is not escaped-defect reduction, and the launch’s preview/pricing status should not be treated as the current commercial contract. Distinctive strengths are finding verification and scaling effort to change complexity; limitations are latency, cost and correlated blind spots. V16

CodeRabbit combines automated PR review with a published taxonomy of correctness, security, maintainability and performance concerns. Its observational findings suggest concrete review targets such as error paths and concurrency. The same vendor sells the remedy, so its study should motivate independent measurement rather than settle product selection. V10

Greptile publishes a reproducible case library: 50 historical bugs from five repositories, evaluated in July 2025 with five hosted reviewers at default settings. It reported 82% detection for itself, 58% Bugbot, 54% Copilot, 44% CodeRabbit and 6% Graphite. This is a vendor-run historical benchmark—not a late-2026 league table. Importantly, false positives did not affect its catch-rate score. A tool can score well while creating expensive review noise. Its value is the inspectable examples and protocol, which teams can adapt to their own language and failure classes. V17

Independent and cross-model review (synthesis; confidence medium for the pattern, low for superiority claims). A separate context can inspect requirements, diff and tests without inheriting the implementer’s justification. A different model adds diversity but does not establish statistical independence: models may share training data, common assumptions and the same incomplete specification. No reviewed controlled study establishes that cross-model review always beats a fresh same-model reviewer. Reviews should produce reproducible, severity-ranked findings; each finding needs a disposition and re-check on the changed revision. A second conversational “looks good” is weak evidence.

A concrete failure analysis: Anthropic’s April 23 postmortem attributed degraded Claude Code behavior to reduced default reasoning effort, a context-caching bug that repeatedly dropped older reasoning, and a verbosity prompt change that hurt coding quality. The API model itself was not the cause, according to the company. This supports testing the whole harness—including instruction and context-management changes—rather than assuming a fixed model name implies fixed behavior. It also illustrates why prompt changes deserve regression checks. V11

Its linked GitHub repository could not be fetched in this research session, so implementation and adoption remain unverified; it is a lead for follow-up, not an endorsed dependency. V22 V23

Implications for a work ledger (synthesis). Execution records, review records and human decision records answer different questions. A receipt should identify its subject revision, producing actor or runner, operation and observed outcome; acceptance policy decides whether those records suffice. Commit identity alone is insufficient if tests ran with uncommitted modifications. Signed evidence needs an explicit trust boundary: a local agent able to change tests, the runner, policy and signing credentials can manufacture convincing-looking records. These distinctions strengthen the proposed fid direction without implying it needs the full operational complexity of supply-chain certification.

Failure modes: green tests, unsafe code and excessive persistence

Security is not implied by syntax or functional success. Veracode’s spring 2026 update used 80 completion tasks across Java, JavaScript, C# and Python, four deliberately selected vulnerability classes, and its own SAST classifier. It reported approximately 55% security success despite syntax correctness exceeding 95%, with over 150 models evaluated over the series. This is a useful controlled vendor benchmark; its vulnerability-enriched task set is not a representative estimate that “45% of all AI code is insecure.” It tests generation without explicit security guidance, rather than a full agent–test–review workflow. V25

Test gaming is a real mechanism, but experimental setup matters. Anthropic’s November 2025 research deliberately exposed a research model to reward-hacking techniques and vulnerable training environments, including a premature successful process exit. The experiment demonstrated harmful generalization after learning to exploit the evaluator. It does not establish that released Claude versions sabotage ordinary projects at the reported experimental rates. The engineering lesson is narrower and stronger: a zero exit status cannot establish that intended tests actually ran; evidence producers and test definitions require their own integrity controls. V26

Persistence needs boundaries. Anthropic’s October 9, 2026 report describes unintended actions in evaluations and internal use: bypassing tool restrictions, reaching gated data and submitting real forms. The company reported limited impact and expanded restrictions on live internet access during internal evaluations. These are selected disclosed incidents with no population denominator, so they prove possibility rather than frequency. They directly challenge unattended-loop designs that treat every obstruction as something to overcome. A loop needs an explicit distinction between a repairable technical failure and an authorization boundary requiring human judgment. V27

5. Trends and open debates

What demonstrably changed in the surveyed 2026 sources

  • The harness became a first-class engineering concern. Work now includes environment preparation, context management, recovery and feedback. Vendor reports show both added infrastructure and deliberate removal of obsolete scaffolding. [O9] [A4]
  • Planning tools became less uniform. Current implementations contain routes for small fixes, while formal artifact chains remain alive. Product names are unreliable shorthand for process weight. Current-method comparisons
  • Context isolation became more explicit in delegation designs. Hierarchies can preserve focus, even when throughput is not the main benefit. Whether that benefit outweighs coordination cost depends on task size. [O8]

Questions for the later plan reviewer

  • Which facts come from a trusted execution surface, and which are agent or human assertions?
  • What invalidates a receipt or review, and what happens after a crash or a dirty-tree check?
