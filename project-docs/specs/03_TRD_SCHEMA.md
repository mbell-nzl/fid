## 1. ID Generation

Generated entity IDs follow the shape `<PREFIX>-<hash>` where:

- **Prefix** is per-entity-type: project prefix (set at `fid init`) for
  issues (`WHET-`, `FID-`); fixed prefixes for other generated
  entities (see table below); `PRD-`/`TRD-` retain their external
  document-derived identifiers (not generated by `fid`).
- **Hash** is `n` hex characters derived from `sha1(uuid4())[:n]`. Using
  a fresh UUID per call (not content-derived) avoids the "two issues
  with the same title collide" failure mode.
- **Progressive length scaling.** Default `n = 6`. When the count of
  rows in the relevant entity reaches a threshold that pushes
  birthday-paradox collision probability above ~1%, new IDs use
  `n = 8`. Old IDs remain valid.
- **Hierarchy is via `parent_id`, not encoded in the ID.** A subtask
  under task `WHET-a1b2c3` has its own hash like `WHET-7c3e9f`, not
  `WHET-a1b2c3.T01`. v1 hierarchy is strict: epics are top-level,
  tasks may belong to an epic or stand alone, and subtasks belong to
  a task.

Drop-in collision handling: on insert, if the generated ID already
exists, retry with a fresh UUID at the configured length. If a
collision appears only after journal merge, `fid rebuild` reports the
conflicting events and requires a human to rewrite one event's ID plus
its same-event references.

Journal event IDs are not entity row IDs. They use the
`EVT-<UTC YYYYMMDD>-<sequence>` shape defined in `02_TRD.md` §4.3 and are
stored in `activity_log.journal_event_id` and `projection_meta.last_event_id`.

### 1.2 Migration Placement

This document is the DDL reference for all roadmap versions. Blocks labelled
with a later version (`v0.2+`, `v0.3`, etc.) are not part of the v0.1 base
migration. Implement migrations by version:

- **v0.1 base:** core issue layer, concerns, requirements, links, claims,
  base telemetry, activity log, projection metadata, labels, roles, and stub
  decision/escalation/triage tables needed by v0.1 FKs/views.
- **v0.2 additive:** workflow tables, role permissions, comments, governance
  command support, agent-run lifecycle/git context columns, and the evidence
  foundation (`gate_executions`, `gate_receipts`, `evidence_records`,
  `evidence_links`) plus extended-economics `agent_runs` columns.
- **v0.3 additive:** QA reviews/findings/plans, QA review claims, templates,
  and QA telemetry extension.
- **v0.4+ additive:** validation contracts/outcomes, carry-forward,
  retrospectives, saved views, export support, and cycles in v0.5.

Triggers and CHECKs are created only when their target table is present in the
active migration. For example, v0.1 does not create comment-scope triggers or
`qa_reviews` checks because those tables ship later.

## 2. Core Issue Layer (v0.1)

```sql
-- 2.1 Unified issues table

CREATE TABLE issues (
  id                  TEXT PRIMARY KEY,        -- e.g. WHET-a1b2c3 (prefix + hash; see §1)
  kind                TEXT NOT NULL,           -- 'epic' | 'task' | 'subtask'
  parent_id           TEXT REFERENCES issues(id),
                                               -- subtask's parent task,
                                               -- task's epic (optional),
                                               -- NULL for epics in v1
  title               TEXT NOT NULL,
  workflow_id         TEXT NOT NULL REFERENCES workflows(id),
                                               -- v0.1: bare enum string ('task-default' |
                                               --   'epic-default' | 'subtask-default'),
                                               --   CHECK-paired with kind.
                                               -- v0.2a (migration 0008): real FK to workflows(id).
  status              TEXT NOT NULL,           -- v0.1: CHECK-constrained per workflow_id.
                                               -- v0.2a (migration 0008): composite FK to
                                               --   workflow_states(workflow_id, state); see the
                                               --   FOREIGN KEY clause below.
  priority            INTEGER,                 -- 0..5 (0 = critical)
  sequence            INTEGER,                 -- positive sibling order; required for tasks
                                               -- under sequential epics, optional for subtasks,
                                               -- NULL for prioritised/unattached tasks
  spec_md_path        TEXT,                    -- canonical spec / brief
  est_tokens          INTEGER,                 -- task/subtask only
  due_date            DATE,
  in_inbox            BOOLEAN DEFAULT 0,       -- unsorted intake, awaiting assignment
  -- Note: concerns_raised and triage_status are NOT stored here.
  -- They are derived via the issues_enriched view (see §2.2).
  owner_role          TEXT,                    -- long-lived ownership (≠ short-lived claim).
                                               -- Defaults: 'tl' for epics, 'developer' for tasks.
                                               -- Set at creation; mutable only via explicit
                                               -- override (journaled; projected to activity_log).
  owner_actor         TEXT,                    -- optional: 'agent' | 'human:<name>'.
                                               -- NULL means "any actor of owner_role".
  created_at          DATETIME, updated_at DATETIME,
  CHECK (kind IN ('epic', 'task', 'subtask')),
  -- v0.1 carried two enum CHECKs here. Migration 0008 REMOVED both — replaced
  -- by the composite FK below, not supplemented (see the note after this block):
  --   CHECK (kind/workflow_id pairing: epic→epic-default, task→task-default,
  --          subtask→subtask-default)
  --   CHECK (per-workflow status enum: task-default IN ('todo','in_progress',
  --          'dev_complete','qa_review','qa_block','failed_gate','qa_pass',
  --          'done','cancelled'); epic-default IN ('todo','in_progress',
  --          'wrapped','closed','cancelled'); subtask-default IN ('todo',
  --          'in_progress','done','cancelled'))
  FOREIGN KEY (workflow_id, status)
    REFERENCES workflow_states(workflow_id, state),
  CHECK (priority IS NULL OR (priority >= 0 AND priority <= 5)),
  CHECK (kind != 'epic' OR est_tokens IS NULL),
  CHECK (sequence IS NULL OR sequence > 0),
  UNIQUE (parent_id, sequence)
);

CREATE TABLE epic_metadata (
  issue_id            TEXT PRIMARY KEY REFERENCES issues(id),
  scheduling          TEXT NOT NULL,           -- 'sequential' | 'prioritised'
  brief_md_path       TEXT,                    -- epic brief (whet's "phase brief" when sequential)
  target_start        DATE,
  target_end          DATE
);
```

**Workflow columns after v0.2a (migration `0008`).** `issues.workflow_id` is a
real FK to `workflows(id)` and `(workflow_id, status)` is a composite FK to
`workflow_states(workflow_id, state)`, so the database rejects any workflow or
state the workflow tables do not define (§3; `02_TRD.md` §4.6). The two v0.1
enum CHECKs are **replaced, not supplemented**. One guarantee is deliberately
not carried over: the database no longer enforces the kind→workflow pairing.
Kind-appropriate defaults are assigned in application code at creation
(`internal/issues`), and Phase 19 (`fid workflow assign`) makes per-kind and
per-project assignment configurable — which that CHECK would have blocked. The
`issues_enriched` view and every trigger defined on `issues` are re-created by
migration `0008`'s table rebuild (§14).

### 2.2 Derived Columns via `issues_enriched`

Two values that callers frequently want alongside an issue —
"are there open concerns?" and "what's the latest triage verdict?"
— are not stored on the `issues` table. They genuinely live in
`concerns` and `triage_events` respectively, and storing them on
`issues` would introduce drift risk for no real benefit.

Instead, a SQL view `issues_enriched` LEFT JOINs the open-concerns
count and the latest `triage_events` row that targets each issue,
exposing the derived values as columns. The CLI's `fid issue get` and
`fid issue list` read from the view, not the base table.

```sql
CREATE VIEW issues_enriched AS
WITH open_concerns AS (
  SELECT issue_id, COUNT(*) AS n
  FROM concerns
  WHERE status = 'open'
  GROUP BY issue_id
),
latest_triage AS (
  SELECT te.*
  FROM triage_events te
  WHERE te.created_at = (
      SELECT MAX(created_at)
      FROM triage_events
      WHERE issue_id = te.issue_id
    )
)
SELECT
  i.*,
  (COALESCE(oc.n, 0) > 0) AS concerns_raised,
  COALESCE(oc.n, 0)       AS open_concerns_count,
  CASE lt.verdict
    WHEN 'RESUME' THEN 'resumed'
    WHEN 'BLOCK'  THEN 'blocked'
    ELSE NULL
  END AS triage_status
FROM issues i
LEFT JOIN open_concerns oc ON oc.issue_id = i.id
LEFT JOIN latest_triage  lt ON lt.issue_id = i.id;
```

Indexes required for the view to perform well:
- `idx_concerns_issue_status` on `concerns(issue_id, status)`.
- `idx_triage_issue_created` on `triage_events(issue_id, created_at)`.

### 2.3 Remaining Issue-Side Tables

```sql
CREATE TABLE acceptance_criteria (
  id                  TEXT PRIMARY KEY,        -- AC-<hash> (see §1)
  issue_id            TEXT NOT NULL REFERENCES issues(id),
  ordinal             INTEGER NOT NULL,
  text                TEXT NOT NULL
  -- Verification state lives in ac_verifications (append-only).
  -- Validation: only valid when issues.kind in ('task', 'subtask').
);

CREATE TABLE ac_verifications (
  id                  TEXT PRIMARY KEY,        -- ACV-<hash> (see §1)
  ac_id               TEXT NOT NULL REFERENCES acceptance_criteria(id),
  verifier_role       TEXT NOT NULL,           -- 'developer' | 'qa_reviewer' | 'qa_lead' | 'tl' | 'human'
  verifier_actor      TEXT,                    -- 'agent' | 'human:<name>' (optional)
  status              TEXT NOT NULL,           -- 'pass' | 'fail' | 'blocked' | 'not_applicable'
  evidence_type       TEXT,                    -- 'test' | 'source' | 'screenshot' |
                                               -- 'manual' | 'command' | 'commit'
  evidence_ref        TEXT,                    -- path / commit hash / command id / URL
  notes               TEXT,                    -- short, free-form
  completion_id       TEXT REFERENCES task_completions(id),
  verified_at         DATETIME NOT NULL
);

-- Append-only by convention; UI never overwrites. A failed verification
-- followed by a passing one from the same role results in two rows.
-- Latest-per-role resolves by journal append order for each
-- (ac_id, verifier_role), using the most recently replayed/appended row.
-- `verified_at` is recorded/displayed but is not the ordering key.
-- Queries that need "verified by every required role" (e.g.
-- all_acs_verified with params_json roles) require at least one 'pass'
-- from each required role since the last completion attempt.

CREATE TABLE task_completions (
  id                  TEXT PRIMARY KEY,        -- TC-<hash> (see §1)
  issue_id            TEXT NOT NULL REFERENCES issues(id),
  attempt_number      INTEGER NOT NULL,
  developer_role      TEXT,                    -- 'developer' (for now)
  model               TEXT,                    -- e.g. 'sonnet-4.6'
  status              TEXT,                    -- 'dev_complete' | 'failed_gate' | 'superseded'
  notes_md_path       TEXT,                    -- prose: "what was implemented"
  actual_tokens       INTEGER,
  commit_hashes       TEXT,                    -- JSON array
  files_touched       TEXT,                    -- JSON array
  expected_files_touched TEXT,                 -- JSON array (hint for v0.5+ file-scope claims)
  gates_passed        INTEGER DEFAULT 0,
  gates_failed        INTEGER DEFAULT 0,
  gate_results        TEXT,                    -- JSON array: [{cmd, exit_code, ran_at, output_excerpt}]
  human_intervention  BOOLEAN DEFAULT 0,
  human_intervention_note TEXT,                -- optional short note when human_intervention=1
  completed_at        DATETIME
);

CREATE TABLE gate_runs (
  id                  TEXT PRIMARY KEY,        -- GATE-<hash> (see §1)
  issue_id            TEXT NOT NULL REFERENCES issues(id),
  attempt_number      INTEGER NOT NULL,
  agent_run_id        TEXT REFERENCES agent_runs(id),
  recorded_by_role    TEXT NOT NULL,
  command             TEXT NOT NULL,
  exit_code           INTEGER NOT NULL,
  output_excerpt      TEXT,
  ran_at              DATETIME NOT NULL,
  CHECK (attempt_number > 0)
);

-- `fid dev gate` writes append-only gate_runs before a completion exists.
-- `fid dev finish`, `fid dev block`, and `fid issue complete` snapshot the
-- gate_runs for the same issue and attempt into task_completions.gate_results
-- and derive gates_passed/gates_failed. Source gate_runs remain as audit rows.
-- From v0.2b (DEC-059/060), gate_runs is the LEGACY reported-evidence table:
-- rows project with trust_source='reported' and cannot satisfy trusted-gate
-- obligations. Trusted evidence lives in gate_executions/gate_receipts (§2.4).
```

### 2.4 Evidence Foundation (v0.2b — draft DDL, DEC-059/060/061)

Draft for the evidence migration; finalize column types/indexes with the
V2-aligned backend-port slice. The earlier live `.fid/gates.toml` registry is
superseded by immutable Gate Definition Registrations created from
project-owned authoring configuration. Their exact projection schema and the
execution/receipt foreign-key updates belong to that joint slice; the draft
below still shows the pre-registration execution columns and must not be
implemented unchanged.

```sql
CREATE TABLE gate_executions (
  id                  TEXT PRIMARY KEY,        -- GX-<hash> (see §1)
  gate_id             TEXT NOT NULL,           -- registry gate ID
  gate_version        INTEGER NOT NULL,        -- registry version executed
  issue_id            TEXT REFERENCES issues(id),
  attempt_number      INTEGER,                 -- derived active attempt when issue-scoped
  agent_run_id        TEXT REFERENCES agent_runs(id),
  trust_source        TEXT NOT NULL,           -- 'executed' | 'attested'
  argv_json           TEXT NOT NULL,           -- snapshot of executed argv array
  cwd                 TEXT NOT NULL,
  timeout_seconds     INTEGER NOT NULL,
  started_by_role     TEXT NOT NULL,
  started_at          DATETIME NOT NULL,
  CHECK (trust_source IN ('executed', 'attested'))
);
-- Append-only start facts, written BEFORE process spawn (TRD §4.3).
-- A row with no gate_receipts child is an abandoned execution:
-- surfaced by fid maintenance check; satisfies nothing.

CREATE TABLE gate_receipts (
  id                  TEXT PRIMARY KEY,        -- RCP-<hash> (see §1)
  execution_id        TEXT NOT NULL UNIQUE REFERENCES gate_executions(id),
  receipt_schema      INTEGER NOT NULL,        -- versioned receipt contract
  producer            TEXT NOT NULL,           -- 'fid <version>' or attested runner identity
  trust_source        TEXT NOT NULL,           -- 'executed' | 'attested'
  status              TEXT NOT NULL,           -- 'pass' | 'fail' | 'timed_out'
                                               -- | 'cancelled' | 'harness_error'
  exit_code           INTEGER,
  signal              TEXT,
  duration_ms         INTEGER,
  branch              TEXT,
  base_commit         TEXT,
  head_commit         TEXT,
  tree_hash           TEXT,                    -- freshness anchor (PRD-EVID-003)
  dirty               BOOLEAN,
  capture_source      TEXT,                    -- 'captured' | 'provided' | 'absent'
  toolchain_fingerprint TEXT,
  stdout_excerpt      TEXT,                    -- bounded + sanitized
  stderr_excerpt      TEXT,                    -- bounded + sanitized
  stdout_hash         TEXT,
  stderr_hash         TEXT,
  stdout_bytes        INTEGER,
  stderr_bytes        INTEGER,
  truncated           BOOLEAN NOT NULL DEFAULT 0,
  redacted            BOOLEAN NOT NULL DEFAULT 0,
  log_artifact_ref    TEXT,                    -- content-addressed local artifact (TRD-SEC-008)
  ended_at            DATETIME NOT NULL,
  CHECK (status IN ('pass','fail','timed_out','cancelled','harness_error')),
  CHECK (trust_source IN ('executed', 'attested')),
  CHECK (status != 'pass' OR exit_code = 0)
);
-- Immutable terminal receipts; at most one per execution (UNIQUE execution_id).
-- Appended only after process termination. Never updated; corrections are new
-- executions. A 'pass' requires exit_code 0 by CHECK; timeouts/signals can
-- never be 'pass'.

CREATE TABLE evidence_records (
  id                  TEXT PRIMARY KEY,        -- EV-<hash> (see §1)
  evidence_type       TEXT NOT NULL,           -- 'receipt' | 'commit' | 'source_state'
                                               -- | 'screenshot' | 'artifact' | 'human_outcome'
  ref                 TEXT NOT NULL,           -- receipt ID / commit hash / path / artifact ref
  recorded_by_role    TEXT NOT NULL,
  human_actor         TEXT,                    -- required when evidence_type='human_outcome'
  human_item          TEXT,                    -- checklist item for human outcomes
  human_outcome       TEXT,                    -- 'pass' | 'fail' | 'blocked' for human outcomes
  note                TEXT,
  recorded_at         DATETIME NOT NULL,
  CHECK (evidence_type != 'human_outcome'
      OR (human_actor IS NOT NULL AND human_item IS NOT NULL
          AND human_outcome IS NOT NULL))
);

CREATE TABLE evidence_links (
  evidence_id         TEXT NOT NULL REFERENCES evidence_records(id),
  ref_type            TEXT NOT NULL,           -- 'ac_verification' | 'qa_review'
                                               -- | 'val_outcome' | 'workflow_gate'
  ref_id              TEXT NOT NULL,
  PRIMARY KEY (evidence_id, ref_type, ref_id)
);
-- Freshness ('current'/'stale'/'missing'/'unverifiable'/'inapplicable') is
-- COMPUTED at read/enforcement time from the receipt's tree identity vs the
-- target tree — it is not stored, so no invalidation writes are needed.
```

## 3. Workflows (shipped v0.2a; seeded from the v0.1 defaults)

The default workflow graphs, status-category mappings, and transition
requirements are listed in `02_TRD.md` §4.6. **The tables below ship in v0.2a
(migration `0007`), seeded verbatim from the v0.1 defaults, and are the runtime
source of truth** — `internal/workflow` loads a read-only registry from them, and
no production code path reads the frozen Go `definitions` map (retained only as
test parity fixtures). Migration `0008` adds the `issues.workflow_id` and
`issues.(workflow_id, status)` foreign keys into `workflows` /
`workflow_states`.

`workflow_transition_requires` intentionally has no PRIMARY KEY or UNIQUE
constraint: an edge may carry several ordered rules, and order is resolved by
`rowid`. Its `params_json` also carries reserved, known-but-unimplemented rule
names: `required_gates_current` and `has_completion` (DEC-066) remain
unseeded and behavior-free until v0.2b, while `linked_to_decision` is seeded
only for `escalation-default` and has no evaluator until v0.2d. The loader
surfaces all three structurally as unimplemented.

```sql
CREATE TABLE workflows (
  id                  TEXT PRIMARY KEY,        -- stable slug, e.g. 'task-default'
  name                TEXT NOT NULL,
  applies_to          TEXT,                    -- 'epic' | 'task' | 'subtask' | 'qa_review' | 'escalation' | NULL (any)
  active              BOOLEAN DEFAULT 1,
  created_at          DATETIME
);

CREATE TABLE workflow_states (
  workflow_id         TEXT NOT NULL REFERENCES workflows(id),
  state               TEXT NOT NULL,
  category            TEXT NOT NULL,           -- 'unstarted' | 'started' | 'completed' | 'cancelled'
  ordinal             INTEGER,
  PRIMARY KEY (workflow_id, state)
);

CREATE TABLE workflow_transitions (
  workflow_id         TEXT NOT NULL REFERENCES workflows(id),
  from_state          TEXT NOT NULL,
  to_state            TEXT NOT NULL,
  PRIMARY KEY (workflow_id, from_state, to_state)
);

CREATE TABLE workflow_transition_requires (
  workflow_id         TEXT NOT NULL,
  from_state          TEXT NOT NULL,
  to_state            TEXT NOT NULL,
  rule                TEXT NOT NULL,           -- 'all_acs_verified' | 'has_completion_report' |
                                               -- 'concerns_addressed' | ...
  params_json         TEXT,                    -- e.g. {"roles":["developer"]};
                                               -- NULL for non-parameterised rules
  FOREIGN KEY (workflow_id, from_state, to_state)
    REFERENCES workflow_transitions(workflow_id, from_state, to_state)
);

CREATE TABLE workflow_assignments (
  scope       TEXT NOT NULL,
  kind        TEXT,
  workflow_id TEXT NOT NULL REFERENCES workflows(id),
  assigned_at DATETIME,
  CHECK (scope IN ('kind', 'project')),
  CHECK ((scope = 'kind' AND kind IS NOT NULL)
      OR (scope = 'project' AND kind IS NULL))
);

CREATE UNIQUE INDEX idx_workflow_assignments_kind
  ON workflow_assignments(kind) WHERE scope = 'kind';

CREATE UNIQUE INDEX idx_workflow_assignments_project
  ON workflow_assignments(scope) WHERE scope = 'project';
```

## 10. Links (Generic Typed-Edge)

```sql
CREATE TABLE links (
  from_type       TEXT NOT NULL,               -- v0.1: 'issue' | 'requirement';
                                               -- v0.2 adds 'decision' | 'escalation'
  from_id         TEXT NOT NULL,
  relation        TEXT NOT NULL,               -- see relation enum below
  to_type         TEXT NOT NULL,               -- same version-gated endpoint set as from_type
  to_id           TEXT NOT NULL,
  created_at      DATETIME,
  PRIMARY KEY (from_type, from_id, relation, to_type, to_id)
);
```

### 10.1 Link Relation Enum

| Relation | Inverse | Semantics |
|---|---|---|
| `blocks` | `blocked_by` | Issue -> Issue. Hard dependency. |
| `relates_to` | `relates_to` | Soft association, no semantic. |
| `duplicates` | `duplicated_by` | Issue -> Issue. |
| `supersedes` | `superseded_by` | Issue -> Issue or Decision -> Decision. |
| `implements` | `implemented_by` | Issue -> Requirement. |
| `caused_by` | `causes` | Issue -> Issue. Root-cause post-mortem links. |
| `discovered_from` | `discovered` | Issue -> Issue. Discovered while working on target. |

Link endpoint scope is version-gated. v0.1 supports issue/requirement
endpoints, with relation compatibility limiting declared links to issue ↔ issue
and issue → requirement. v0.2 adds `decision` and `escalation` endpoints when
the governance entities and commands ship. `relates_to` is the only relation
allowed across any two endpoint types supported by the current schema version.

The generic link table is not a second encoding for lifecycle
relationships that already have dedicated schema. Do not use `links`
for hierarchy (`issues.parent_id`), QA review scope, concern/finding
escalation, escalation resolution, AC-assertion coverage, or QA plan
step-assertion coverage.

The CLI auto-creates the inverse on every link add so callers only declare one
direction. `fid link remove` accepts the same declared direction and removes
both the declared row and its inverse row in the same journal event. Removing a
nonexistent link is rejected with an error naming the missing relation and
entities.

## 11. Claims (Exclusive-Access Leases)

```sql
CREATE TABLE claims (
  ref_type        TEXT NOT NULL,               -- v0.1: 'issue'; v0.3+: 'qa_review'
  ref_id          TEXT NOT NULL,
  claimed_by      TEXT NOT NULL,               -- role string
  claimed_at      DATETIME NOT NULL,
  ttl_seconds     INTEGER NOT NULL DEFAULT 1800,
  note            TEXT,
  PRIMARY KEY (ref_type, ref_id)
);
```

### 11.1 Claim Semantics

Claims are short-lived exclusive-access leases on individual entity
rows. They sit alongside `status` and `activity_log`, not in place of
them:

- **Status** records what state the work is in.
- **Activity log** projects who did what and when for query/display.
- **Claim** records who currently holds the right to advance the work.
- **Ownership** (separate, on `issues.owner_role` /
  `issues.owner_actor`) records who is accountable for the work
  across its lifetime. Claims are short-lived (minutes); ownership is
  long-lived (an epic's full duration).

Rules:

- An entity may have at most one live claim at a time.
- Acquiring a claim is atomic. Concurrent `claim acquire` calls on the
  same entity: exactly one wins; the rest see "already claimed by X
  until T."
- Transitions into a `started`-category state require a live claim by
  the caller. Transitions out clear the claim automatically.
- A claim expires `ttl_seconds` after `claimed_at`. Stale claims do
  not block re-acquisition; the new caller's `claim acquire --force`
  (or implicit on stale) takes over and the prior holder is recorded
  in the journal and projected into `activity_log` as superseded.
- The current claim holder may renew a live claim. Renewal updates
  `claimed_at` to the renewal time and uses the supplied TTL, or keeps
  the previous TTL when none is supplied. Renewal by any other role is
  rejected unless it is a force-acquire by a role permitted to force-acquire.
- Humans can claim entities too (`--by human`) to signal "agent hands
  off while I think about this."

Entities supporting claims in v0.1: `issues`. v0.3 adds `qa_reviews`.

### 12.1 Coverage Rules (enforced when contract+plan present)

When a contract is `active` and a plan is `active` for the same epic,
fid enforces these invariants at plan-finalisation time
(`fid qa-plan finalise`):

- Every requirement linked to the epic (via `links` with relation
  `implements`) is referenced by at least one assertion.
- Every assertion has at least one referencing AC OR an explicit

requirements are CHECK constraints on `val_assertion_outcomes`.

## 14. Validation Triggers

**Application-layer primary, SQLite triggers as backstop.** The application
layer handles all validation on the CLI write path. Triggers serve as a
backstop for writes that bypass the CLI (future web dashboard, `fid sql`,
direct DB edits). Each migration creates only the triggers whose target tables
exist in that schema version.

### 14.1 Kind-Invariant Rules

BEFORE INSERT / UPDATE triggers on:

- **`issues.parent_id`** — epics must have no parent; tasks may have no
  parent or an epic parent; subtasks must have a task parent.
- **`issues.sequence`** — tasks under sequential epics must have a
  sequence; tasks under prioritised epics or no epic must not;
  subtasks may use sequence for sibling display order, but v1 does
  not assign readiness semantics to subtask ordering.
- **`acceptance_criteria`** — `issue_id` must reference a `task` or
  `subtask`.
- **`task_completions`** — same.
- **`epic_metadata`** — `issue_id` must reference an `epic`.
- **`qa_reviews`** (v0.3) — `epic_id` references an epic when set; `task_id`
  references a task when set.
- **`qa_review_task_window.task_id`** (v0.3) — references a task.
- **`triage_events.epic_id`** — references an epic.
- **`decisions.epic_id`** — references an epic when set.
- **`carry_forward.scheduled_epic_id`** — references an epic when set.

Static issue-column invariants are CHECK constraints in the `issues` DDL:
v0.1 kind/workflow compatibility, legal status values for the active default
workflow, priority range, epic estimate nullability, and positive sequence
values. The application layer still owns transition edge legality and
transition-rule evaluation because those need rich errors, current actor role,
and multi-row reads.

### 14.2 Polymorphic Ref Integrity

BEFORE INSERT triggers on `links`, `claims`, and `activity_log` validate that
`(ref_type, ref_id)` resolves to an existing row in the named table. The
equivalent `comments` trigger ships with the v0.2 comments table.

### 14.3 Link Scope and Relation Compatibility

BEFORE INSERT triggers on `links` reject endpoint types outside the active
schema-version scope: v0.1 accepts `issue` and `requirement`; v0.2 adds
`decision` and `escalation`. They also reject relation/entity combinations that
duplicate dedicated schema relationships.

### 14.4 Claim Scope

BEFORE INSERT / UPDATE triggers on `claims` reject unsupported
`ref_type` values for the active schema version. v0.1 supports only
`issue`; v0.3 adds `qa_review`.

### 14.5 Comment Scope

BEFORE INSERT / UPDATE triggers on `comments` reject `ref_type` values
outside the active schema-version scope. v0.2 supports `issue`,
`decision`, `escalation`, and `requirement`; v0.3 adds `qa_review`.

### 14.6 Activity-Log Projection Discipline

`activity_log` inserts are allowed only while applying journal event
effects. It is a read-model table, not an independent write surface.

### 14.7 Kind Immutability

A BEFORE UPDATE OF kind trigger on `issues` rejects any attempt to
change `kind` after creation.

### 14.8 Mutually-Exclusive Scope Columns

Expressed as a CHECK constraint in the `qa_reviews` DDL:
```sql
CHECK ((scope = 'single_task' AND task_id IS NOT NULL AND epic_id IS NULL)
    OR (scope IN ('epic_window', 'epic_full') AND epic_id IS NOT NULL AND task_id IS NULL))
```

### 14.9 Validation Outcome Checks

`val_assertion_outcomes` uses row-local CHECK constraints for static outcome
rules:

```sql
CHECK (outcome IN ('pass', 'fail', 'carry_forward'))
CHECK (outcome != 'pass' OR (evidence_method IS NOT NULL AND evidence_ref IS NOT NULL))
CHECK (outcome != 'carry_forward' OR rationale IS NOT NULL)
```

Required-validator satisfaction is cross-row: the latest `pass` outcome must
match `assertion_id`, `recorded_by_role`, and `evidence_method` against a
`validation_assertion_validators` row. That rule is enforced by application
validation during outcome recording, plan finalisation, and contract reporting,
because SQL CHECK constraints cannot express "latest matching row" semantics.

### 14.10 What Does Not Get a Trigger

Workflow transition rules, permissions, AC verification freshness,
required-validator satisfaction, template validation. These all need rich
context, multi-table reads, ordering, or runtime state (calling role) that SQL
doesn't have. They live in app-layer code exclusively, with `fid maintenance
check` as the periodic audit.

### 14.11 Maintenance Structural-Audit Parity

`fid maintenance check` is read-only: it reports every discovered violation and
never repairs projection rows or appends a journal event. Its structural-error
pass mirrors the active v0.1 trigger-backed rules that can be invalidated by a
corrupt or externally modified projection:

- issue hierarchy; task sequence/scheduling; and the kind requirements for
  acceptance criteria, task completions, epic metadata, schema-only decisions,
  and schema-only triage events;
- v0.1 link endpoint scope, endpoint resolution, and relation compatibility;
  v0.1 claim scope and issue resolution; and activity-log supported type and
  target resolution;
- every row returned by `PRAGMA foreign_key_check`; and
- each issue's `(workflow_id, status)` pair against the projected workflow
  tables (§3), resolved through the read-only workflow registry. As of v0.2a
  this is the migrated source of truth; the audit no longer consults the frozen
  v0.1 Go definitions, which survive only as test parity fixtures. Behavior is
  otherwise unchanged — an unknown pair is a structural error; and
- **workflow-assignment compatibility** (v0.2a, DEC-105). Each
  `workflow_assignments` row is checked against its workflow's `applies_to`: a
  kind-scope row whose workflow is bound to a different kind, and a project-scope
  row whose workflow is not `any`, are each a structural error naming the
  offending assignment. Foreign-key integrity for the same table is already
  covered by the `PRAGMA foreign_key_check` pass above and is not duplicated
  here.

For every `activity_log` row, the audit also resolves `journal_event_id` in the
append-only journal using the journal inspection path. A missing journal event
is a structural error even though activity rows do not have a SQLite foreign
key to journal storage. Findings are deterministic by check, entity ID, then
message.

**Table scope (corrected v0.2a, DEC-105).** This audit previously excluded every
table that does not exist in v0.1. That exclusion no longer holds: v0.2a's
projected `workflow_assignments` table is audited by the check above. The rule
is now that a projected table is audited once it has a structural invariant that
a corrupt or externally modified projection could violate — not that it shipped
in v0.1.

## 15. Required SQLite Pragmas

```sql
PRAGMA foreign_keys = ON;
PRAGMA recursive_triggers = ON;
```

Set on every connection open.

The `fid rebuild` connection additionally sets `synchronous = OFF` and
`journal_mode = MEMORY` (DEC-071); `foreign_keys` and `recursive_triggers` remain
ON and the normal command path keeps full durability. See `02_TRD.md` §4.4 for
the rationale.
