# DESIGN PLAN — fid

> This document defines the intended user experience across fid's surfaces:
> CLI output formatting, TUI board design, and shared design conventions.
> It guides agent implementation decisions without prescribing pixel-level
> detail.

---

## 1. Experience Principles

1. **Machine-readable by default, human-readable on demand.** JSON output
   for every read command ensures universal pipeability. Humans opt in via
   `--format markdown`; token-efficient agents opt in via `--format toon`.
   The discoverable path is the working path.
2. **Errors that teach.** Every rejection names the specific constraint
   violated, the entities involved, and the corrective action. An agent
   should be able to parse the error and self-correct without human help.
3. **One command, one answer.** Cross-cutting questions that today require
   multi-file grep and agent interpretation should resolve in a single
   `fid report` or `fid stats` invocation. Minimize round trips.
4. **Composites over ceremonies.** Role-namespace commands (`fid dev
   finish`, `fid qa start`, `fid triage verdict`) compose primitives into
   the right sequence for a role's workflow. Agents do one call instead of
   remembering five. Primitives remain available for edge cases.
5. **Respect the terminal.** Assume 80-column minimum width. No colour in
   piped output. Structured output on stdout; messages on stderr.

## 2. Surfaces

| Surface | Primary Jobs | Constraints | Verification |
|---|---|---|---|
| `fid` CLI | All reads and writes; primary interface for agents and humans | Single Go binary; stdout is machine-parseable by default; stderr for diagnostics. < 500ms per read at 10k issues. | Integration tests per command; output snapshot tests. |
| TUI board (v0.3) | Visual kanban of issues by status category | Terminal-based; 80-col minimum; keyboard-navigable | Manual verification + screenshot comparison |
| MCP server (v0.3) | Agent integration via Model Context Protocol | Localhost only; curated tool subset, not full CLI | Integration tests against MCP SDK |
| Markdown export (v0.4) | Human-readable project state as a file tree | YAML frontmatter contract; "generated by fid" banner | Export round-trip tests |
| Web dashboard (v0.5) | Browser-based project visualisation | Reads SQLite directly; separate package | Deferred to v0.5 design |

### 3.2 Entity Hierarchy

```text
Epic (top-level container)
├── Task (implementable work item)
│   ├── Subtask (decomposed part)
│   ├── Acceptance Criteria
│   │   └── AC Verifications (append-only, per role)
│   ├── Task Completions (append-only, per attempt)
│   │   └── Concerns (developer-raised flags)
│   └── Agent Runs (telemetry)
├── QA Reviews (scoped to window / single task / full epic)
│   └── QA Findings (blocking / improvement)
├── Decisions (durable choices)
├── Escalations (unresolved situations)
├── Triage Events (TL-Lite verdicts)
└── Retrospectives (epic wrap-up)
```

## 4. Interaction Patterns

| Pattern | Use When | Required Behavior |
|---|---|---|
| Primitive command | Caller needs fine-grained control or is composing a custom sequence | Validate inputs, enforce permissions via `--by`, apply workflow rules, produce one journal event, return structured result |
| Composite command | Agent is performing a standard role workflow step | Compose primitives atomically (one journal event with multiple effects); reject entirely on partial failure |
| Ready queue | Agent needs the next actionable task | Return one task (or empty with explanation); respect epic scheduling mode (sequential vs prioritised) |
| Context pack (v0.2) | Agent needs role-tuned context for an issue | Bundle issue + role-relevant related data in one response; minimize follow-up reads |
| Named report | Cross-cutting query across entities | Return pre-composed SQL result; support `--format` override |
| SQL escape hatch | Ad-hoc inspection not covered by reports | Accept only SELECT/EXPLAIN/PRAGMA/WITH; reject mutations; return tabular result |

## 5. Output Standards

### 5.1 Format Strategy

| Format | Trigger | Shape |
|---|---|---|
| JSON (default) | No `--format` flag, or `--format json` | Object for `get` commands; array for `list` commands. Field names use snake_case matching DB columns. |
| TOON | `--format toon` | Token-efficient tabular encoding. Same logical shape as JSON. Recommended for agent `list` invocations. |
| Markdown | `--format markdown` | Human-readable rendering with headers, tables, and status indicators. |
| YAML | `--format yaml` | YAML serialisation. Useful for config and template authoring. |

### 5.2 JSON Output Conventions

- `get` commands return a single JSON object.
- `list` commands return a JSON array (empty array `[]` when no results).
- All timestamps use ISO 8601 format (`2026-05-27T14:30:00Z`).
- Null fields are included in output (not omitted) for schema
  predictability.
- Nested relationships are included inline where the query naturally
  joins them (e.g. ACs within an issue get), not as separate top-level
  arrays.
- IDs are always strings, even when they look numeric.

### 5.3 Message Output Channels

| Flow | Channel | Prefix | Exit Code |
|---|---|---|---|
| Structured result | stdout | (none — raw JSON/TOON/markdown) | 0 |
| Success confirmation (writes) | stderr | (none — terse one-liner) | 0 |
| Warning | stderr | `warning:` | 0 |
| Error | stderr | `error:` | non-zero |
| Empty result with explanation | stdout | (empty result set) + stderr note | 0 |

**Rules:**
- Stdout is always machine-parseable. Never mix diagnostics into stdout.
- Stderr carries human-readable messages: confirmations, warnings, errors.
- When stdout is a pipe (not a TTY), suppress any decorative output.
- Exit code 0 for successful operations including empty result sets.
  Non-zero only for actual failures (invalid input, constraint violation,
  I/O error).

### 5.4 Error Message Standard

Per PRD-NFR-003, every error message must include:

1. **The specific constraint violated** — name the rule, not just "invalid".
2. **The entities involved** — include IDs so the caller can inspect.
3. **Corrective action** where applicable — what to do next.

```text
error: transition from "todo" to "dev_complete" is not allowed
  permitted transitions from "todo": in_progress
  issue: FID-a1b2c3

error: role "intern" not in project profile
  known roles: developer, qa_reviewer, qa_lead, tl_lite, tl, workflow_runner, human

error: cannot transition to "dev_complete": 2 of 4 ACs not verified by developer
  unverified: AC-7c3e9f, AC-d4e5f6
  issue: FID-a1b2c3

error: already claimed by developer until 2026-05-27T15:00:00Z
  issue: FID-a1b2c3
  to force-acquire: fid issue unclaim FID-a1b2c3 --force
```

### 5.5 Empty State Standard

Empty results are not errors. The system returns:

- **stdout:** The empty representation for the format (empty JSON array
  `[]`, empty TOON table, etc.).
- **stderr:** A human-readable explanation of why no results were found.

```text
# stdout
[]

# stderr
note: no ready tasks — all 3 tasks in FID-e1f2g3 are blocked or completed
```

### 5.6 Write Confirmation Standard

Write confirmations go to stderr. Brief, informative, not chatty:

```text
created issue FID-a1b2c3 (task) "Add OIDC discovery endpoint"
transitioned FID-a1b2c3: todo → in_progress
verified AC-7c3e9f on FID-a1b2c3 by developer: pass
claimed FID-a1b2c3 by developer (expires 2026-05-27T15:00:00Z)
```

## 7. TUI Board Design (v0.3)

### 7.1 Layout

```text
┌─ fid board ──────────────────── FID-e1f2g3: Core persistence ─┐
│                                                                │
│  UNSTARTED      │ STARTED         │ COMPLETED    │ CANCELLED   │
│  ───────────    │ ─────────       │ ──────────   │ ──────────  │
│  □ FID-g7h8i9   │ ▶ FID-a1b2c3   │ ✓ FID-d4e5f6 │             │
│    Schema mig.  │   Journal flush │   Init cmd   │             │
│    P1           │   P1 ⚠2 AC     │   P0         │             │
│                 │                 │              │             │
│  □ FID-j0k1l2   │ ▶ FID-m3n4o5   │ ✓ FID-p6q7r8 │             │
│    Rebuild cmd  │   Claim acquire │   ID gen     │             │
│    P2           │   P2            │   P1         │             │
│                 │                 │              │             │
└────────────────────────────────────────────── 6 tasks · 2 done ┘
```

### 7.2 Design Notes

- Columns grouped by status category, not individual status.
- Each card shows: issue ID, title (truncated), priority, and flag
  indicators (open concerns ⚠, unverified ACs, blocked status).
- Keyboard navigation: arrow keys to move between cards, Enter to
  view issue detail, `/` to filter, `q` to quit.
- Filterable by epic, labels, status category, and priority.
- Footer shows summary counts.
- Built with `charmbracelet/bubbletea` + `lipgloss`.

## 8. Cross-Surface Parity Matrix

| Concept | CLI JSON | CLI Markdown | TUI Board | MCP Server | Markdown Export |
|---|---|---|---|---|---|
| Issue status | `status` field | Status heading | Column placement | Resource field | Frontmatter `status:` |
| Status category | `status_category` field | Derived from status | Column header | Resource field | Frontmatter `status_category:` |
| Open concerns | `concerns_raised` boolean + count | "⚠ N open concerns" line | ⚠ indicator on card | Included in resource | Section in task export |
| AC verification state | Per-role object | Checkbox + role badge | AC count indicator | Included in resource | `- [x]` / `- [ ]` checkboxes |
| Priority | Integer 0–5 | P0–P5 label | P0–P5 on card | Integer field | Frontmatter `priority:` |
| Claim state | Separate `claim` field when present | "Claimed by X until T" line | Lock indicator on card | Separate resource | Not exported |

## 9. Human Verification Guidance

These judgments require human review and cannot be automated:

- **Error message clarity.** Are constraint violation messages
  understandable without reading the source code? Can an agent parse
  them and self-correct?
- **Workflow friction.** Does the composite-then-primitive layering
  feel right? Are agents reaching for primitives because composites
  don't fit their workflow?
- **Output density.** Is the JSON shape predictable enough that agents
  don't need to inspect it? Is the markdown format scannable for humans?
- **TUI usability.** Does the kanban board provide useful orientation, or
  is `fid issue list` faster for the actual use case?
- **Ready queue accuracy.** Does `fid ready` consistently return the task
  a human would pick next? Are the scheduling heuristics (sequential
  vs prioritised) behaving as expected?
- **Dogfooding fit.** Does fid replace the daily grep-and-read patterns
  from whet's markdown workflow, or does the CLI ceremony add friction
  that outweighs the query power?

## 10. Scenario Candidates

| Theme | Risk It Covers | Target Release / Phase |
|---|---|---|
| Developer task loop: ready → claim → implement → finish | Core happy path for the primary use case | v0.1 |
| Concurrent agent writes in the same checkout | Data integrity under SQLite serialisation | v0.1 |
| Sequential epic with a blocked mid-sequence task | Ready queue returns no task and reports the blocker correctly | v0.1 |
| QA reviewer mid-epic review with blocking finding | Finding → escalation → triage → resolution flow | v0.3 |
| TL epic wrap-up with unresolved escalations | Transition rules prevent premature closure | v0.2 |
| Journal corruption recovery: malformed trailing line | Rebuild stops and reports, does not silently skip | v0.1 |
| Cross-branch journal merge with conflicting writes | Text-based merge of JSONL, then rebuild reconciles | v0.1 |
| Agent with wrong role attempts forbidden action | Permission enforcement with actionable error message | v0.1 |
